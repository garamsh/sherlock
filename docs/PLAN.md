# 프로젝트 초기 구성 지시서 (Initial Agent Prompt — MVP)

당신은 이 프로젝트의 초기 아키텍처를 구성하고 MVP를 빠르게 세워야 하는 엔지니어링 에이전트입니다. "MVP"는 기능 범위가 작다는 뜻이지, 코드 품질이 낮아도 된다는 뜻이 아닙니다. 스코프는 최소화하되, 인터페이스 설계와 에러 처리, 확장 가능성은 프로덕션 기준으로 작성하세요.

## 1. 프로젝트 목표

OpenClaw류 자율 에이전트 플랫폼을 만들되, 다음 원칙을 따른다.

- **3요소 구조**: Gateway / Agent / Tool. 계층을 늘리지 않고 이 세 컴포넌트만으로 시스템을 구성한다.
- **Tool이 서비스를 구성한다**: 외부 서비스든, 실행 샌드박스든, 메모리 관리든 전부 Agent가 호출하는 "Tool" 하나로 취급한다. 특별 취급되는 서브시스템을 따로 만들지 않는다.
- **에이전트는 자신의 실행 환경에 대해 전적 권한을 가진다**: 에이전트가 올라가는 환경(Docker 컨테이너) 내부에서는 제약을 두지 않는다. 대신 그 환경의 경계(네트워크, 마운트, 리소스, 생명주기)는 오케스트레이션 레이어가 관리한다.
- **메모리는 RAG 기반이면서 에이전트가 능동적으로 관리한다**: 단순 저장/검색이 아니라, 사람의 기억처럼 갱신·압축·삭제가 일어난다.

## 2. 아키텍처 개요

```
[ 외부 채널: Web, API, 메신저, CLI ]
              │
      ┌───────▼────────┐
      │     Gateway     │  ← 채널 정규화 + 라우팅/세션/인증
      └───────┬────────┘
              │ 표준 메시지 포맷
      ┌───────▼────────┐
      │      Agent      │  ← 추론 루프 + 오케스트레이션
      └───────┬────────┘
              │ 표준 도구 호출 프로토콜
      ┌───────▼────────┐
      │      Tool       │  ← memory / sandbox_exec / 외부 서비스 커넥터 등
      └─────────────────┘         (모두 동일한 Tool 인터페이스)
```

세 컴포넌트 외의 개념(Plugin System, Skill System, Memory System 등)을 별도 계층으로 명명하지 말 것. 전부 Tool의 구현체 중 하나로 취급한다.

### 2.1 Gateway
- 멀티 채널 어댑터를 내부에 두되, 외부에는 단일 진입점만 노출.
- 세션/인증/라우팅 담당. 채널 추가 = 어댑터 하나 추가로 끝나야 한다.

### 2.2 Agent
- 멀티턴 추론 루프(모델 호출 → 도구 호출 판단 → 실행 → 결과 반영 → 반복).
- 도구 레지스트리를 들고 있으며, 등록된 Tool의 스키마를 보고 언제 어떤 Tool을 호출할지 스스로 판단한다.
- 메모리 관련 판단(저장할지, 압축할지, 잊을지)도 Agent의 추론 루프 안에서 memory tool 호출로 처리한다 (3장 참고).

### 2.3 Tool
- 모든 기능은 동일한 인터페이스(이름, 입력 스키마, 출력 스키마)로 등록된다.
- MVP에서 반드시 있어야 할 Tool:
  - `sandbox_exec`: 실행 샌드박스 제어 (아래 4장)
  - `memory`: 기억 관리 (아래 3장)
  - 그 외 예시 서비스 커넥터 1~2개 (예: 웹 검색, 파일 처리 등 — 프로젝트 성격에 맞춰 선택)

## 3. 메모리: RAG + 에이전트 주도 관리

단순 store/search가 아니라, 아래 다섯 오퍼레이션을 가진 `memory` tool로 구현한다.

| 오퍼레이션 | 역할 |
|---|---|
| `store` | 새로운 기억을 저장 (원문 + 임베딩 + 메타데이터) |
| `search` | 하이브리드 검색(벡터 + 키워드)으로 관련 기억 조회 |
| `update` | 기존 기억 내용 수정 (예: 새로운 정보로 덮어쓰기) |
| `compress` | 여러 개의 세부 기억을 요약해 상위 기억으로 압축 (consolidation) |
| `forget` | 중요도/최신성이 낮은 기억을 삭제 또는 아카이브 |

설계 포인트:

- **메타데이터 스키마**: 최소한 `timestamp`, `importance_score`, `access_count`, `last_accessed`, `source(session/tool 등)`를 포함한다.
- **에이전트가 판단 주체**: Agent가 대화/작업 중 "이건 기억해둘 만하다"고 판단하면 `store`를 호출하고, 특정 주기(세션 종료 시 또는 저장소가 임계치를 넘을 때) 마다 스스로 `compress`/`forget`을 호출하는 reflection 루틴을 둔다. 이 판단 로직 자체도 Agent 추론 루프의 일부로 둘 것 — 별도의 "메모리 매니저 에이전트" 같은 걸 새로 만들지 않는다.
- **저장소**: 벡터 스토어(pgvector/Qdrant/Chroma 중 택1, MVP에서는 가장 셋업이 빠른 것 선택) + 키워드 인덱스(BM25 등)를 함께 둔다. 두 결과를 합쳐 랭킹하는 간단한 하이브리드 스코어링 함수 하나만 MVP 범위에 포함한다(고도화된 re-ranking은 이후 단계).
- **압축(compress)의 형태**: 오래되었거나 유사한 다수의 세부 기억을 LLM 호출로 요약해 하나의 상위 레벨 기억으로 대체하고, 원본은 아카이브(즉시 삭제하지 않음 — 필요시 롤백 가능하게).

## 4. 실행 샌드박스: sandbox_exec Tool

- 에이전트는 Docker 컨테이너 위에서 실행되며, **컨테이너 내부에서는 완전한 권한**(필요시 root 포함)을 가진다.
- **프로젝트 책임 범위**: 컨테이너 생성/파기, 네트워크 egress 정책(도메인 allowlist), 볼륨 마운트 범위, 리소스 쿼터(CPU/메모리/프로세스 수), 세션 단위 ephemeral 생명주기(작업 종료 시 파기).
- **프로젝트 책임 범위 밖**: gVisor, Firecracker 등 커널 레벨 격리 런타임 선택 및 구성은 호스트 관리자의 책임으로 둔다. 우리 코드는 어떤 컨테이너 런타임이 아래 깔려도 동작하도록 표준 Docker API만 사용한다.
- `sandbox_exec` tool은 최소한 `create`, `exec(command)`, `destroy` 오퍼레이션을 가진다.

## 5. 초기 작업 목록 (MVP)

1. 저장소 최상위 구조: `gateway/`, `agent/`, `tools/` (memory, sandbox_exec 서브모듈 포함)
2. Tool 공통 인터페이스(이름/입력 스키마/출력 스키마) 정의 — 이후 모든 Tool이 이 인터페이스를 따름
3. Gateway: 채널 1개(HTTP API 또는 WebChat) 어댑터 + 세션 관리 최소 구현
4. Agent: 추론 루프 + 도구 레지스트리 + 도구 호출 스켈레톤
5. `memory` tool: store/search 우선 구현 → update/compress/forget은 인터페이스만 정의하고 최소 동작으로 구현
6. `sandbox_exec` tool: Docker 기반 create/exec/destroy 구현, 네트워크 egress allowlist 적용
7. 위 전체를 관통하는 통합 시나리오 1개(예: "질문 → 관련 기억 검색 → 샌드박스에서 코드 실행 → 결과를 기억에 저장") end-to-end 테스트

## 6. 제약사항

- Go 언어를 선정하였으며, 프로젝트는 영어로 진행된다. (코드, 주석, 문서 모두 영어)
- Gateway / Agent / Tool 세 컴포넌트 외의 이름을 가진 계층을 새로 만들지 말 것. 새로운 기능이 필요하면 우선 "이건 Tool로 표현 가능한가"를 먼저 검토한다.
- MVP 범위를 넘는 고도화(예: re-ranking, 멀티 에이전트, 지식 그래프)는 인터페이스에 확장 여지만 남기고 구현하지 않는다.
