# ADR 0008: Agent-influenced sub-processes run dropped to the unprivileged UID

> Status: accepted
> Date: 2026-07-30 (revised in place 2026-08-13; 2026-08-16; 2026-08-17; 2026-10-09; 2026-10-10)

## Context

The agent needs general-purpose exec for real workloads: "run the project's test suite and report which tests fail", "find all files larger than a size and list them", "compute a value with awk / jq / sed instead of inline in the model", "run a one-off pipeline on a workspace file". Typed tools cover typed needs; exec covers the rest. The workspace is the computer (ADR 0017): it serves the filesystem AND runs agent-influenced processes, so the trust boundary for those sub-processes is decided here, once, at the workspace that owns the executor.

The privileged drop needs a root workspace with `SYS_ADMIN`, which PodSecurity `restricted` cannot admit and `baseline` does not allow. The only Kubernetes deployment runs under `restricted` and its consumers keep it there (#1049): its workspace runs as uid 65532 with every capability dropped and `exec-uid` set to its own uid, in a container where `/proc/sys/user/max_user_namespaces` reads `0` and `unshare --user --net true` fails with `Operation not permitted` (measured by gitops on 2026-10-10, #1049). The sysctl is not the only thing refusing the clone. In a `restricted` probe Pod under `RuntimeDefault` — which the cluster applies to every Pod, its kubelet running `seccompDefault: true` — `unshare` with `CLONE_NEWUSER`, with `CLONE_NEWUSER|CLONE_NEWNET` and with `CLONE_NEWNET` each returned `EPERM`, with `Seccomp: 2` and `CapEff: 0`. An exhausted user-namespace limit returns `ENOSPC` or `EUSERS` rather than `EPERM`, and the seccomp filter runs at syscall entry, before the limit is consulted, so the `EPERM` is the profile's (gitops, 2026-10-10, #1052). That is a strong reading and not a proof: the control that would settle it, a node with the sysctl raised and the Pod `Unconfined`, needs an infra node and has not been run. A second consumer, garam's Docker standalone supervisor, runs the privileged drop and depends on it.

## Decision

When the workspace's executor (`internal/workspace/shell`, ADR 0017) spawns a child for agent-influenced work, the child runs as the unprivileged exec UID: dropped to it in the privileged drop, already running as it in the unprivileged shape (Consequences). The file side of the same boundary stands in the same process: workspace writes and exec'd children share the workspace directory's ownership story.

The model-facing surface is a tool: `shell_exec` is an independent tool server (ADR 0017, ADR 0009) that wraps the workspace's Exec RPC. The model reaches exec through the same tool-call channel as every other capability. The agent itself executes nothing — the tool calls the workspace over the gRPC client. Exec children work in the workspace directory by default, so an exec'd program sees the same files the file tools sees natively — the workspace execs children in its own directory and no shared-mount trick is needed.

Mechanism:

- The executor forks, sets the child to the exec UID, drops Linux capabilities, applies resource limits, and execs the command.
- Network isolation is per-request (`NoNetwork`): the child lands in a fresh, empty network namespace (a privileged unshare, or an unprivileged user+network namespace in the unprivileged shape, ADR 0010); in the pod topology the pod network layer is an additional mechanism.
- The child can neither read nor write the agent's volume — `memory.db`, its sidecars and `outbox/` — and what holds that in full is the mount: the agent's volume is not mounted into the workspace container, so no child reaches it under any account. In the privileged drop the distinct exec UID holds it as well, and on a volume both containers mount it stops reads as well as writes: the agent creates `memory.db`, its sidecars and the writer lock `0600` and `outbox/` `0700`, and tightens an existing store to those modes at startup (#998). What it leaves visible there is names: the directory holding `memory.db` stays `0755`, because it may also hold the workspace directory, which an Exec child must traverse. Platform runtime material is out of reach by kernel DAC.
- The child has a configurable timeout; on expiry its whole process group is SIGKILLed and the result carries `timed_out: true` — a normal outcome crossing the wire, not an RPC error. The group, not the child alone: the child is the shim, which execs a shell, which execs the command, and each inherits the pipe the executor drains, so killing only the first leaves the caller waiting for the last.
- That kill crosses the drop, so it needs a capability the drop does not: signalling a process that owns neither of the executor's uids requires `CAP_KILL`, and root is no substitute once the capability has left the bounding set. **The claim above holds only where the workspace holds `CAP_KILL`** — the unprivileged shape excepted, where the child owns the executor's own uid. A privileged executor without it reports `agent_uid unavailable` per call rather than running a command whose deadline it could not enforce (#612).
- When the platform cannot run the child as the configured account, the executor reports `agent_uid unavailable` instead of silently upgrading.
- When the platform cannot apply one of the child's resource limits, the executor fails the call instead of running the child uncapped. The same holds for the one bound the executor owns rather than the child: a deadline it could not enforce fails the call.

Threat model (honest):

- A child can read everything under the workspace (this is its purpose) and can leak workspace contents through covert channels; containers do not fix that.
- A child **cannot** read secrets (ADR 0003), modify the tool runtime, or make network requests unless the operator sanctioned egress — enforced structurally.

What exec is NOT:

- Not hosted in the agent — the agent process holds no exec machinery; the `shell_exec` tool is a client of the workspace contract.
- Not a general-purpose programming environment exposed to the model — typed tools first; exec is for what the typed surface does not cover.

## Consequences

- The `internal/workspace/shell/` package holds the executor; the Executor interface is the only thing the workspace server uses, so added hardening (chroot, seccomp, more rlimits) is a swap, not a rewrite. `shell_exec` is an independent tool server (ADR 0017) that calls the workspace's Exec RPC; it knows only the workspace gRPC client.
- Two deployment shapes are supported, and an operator chooses one explicitly; neither is a fallback for the other.
  - **The privileged drop.** A workspace process with UID-switch privilege (setuid-root binary, supervisor, or container capabilities) runs children as a configured exec UID that is not its own. It is the only shape with a uid boundary between an Exec child and the workspace process.
  - **The unprivileged shape.** The workspace runs as a non-root uid with no added capability, and `exec-uid` is set to that same uid — declared explicitly, with no implicit fallback to the current UID. It is supported on four requirements, each a property of the deployment rather than something the workspace checks: the agent's volume is not mounted into the workspace container; the workspace container does not share a process namespace with the agent container; and two host requirements, both infra artifacts, that together let that uid create a user and network namespace (ADR 0010) — `user.max_user_namespaces` above `0` on the node, and a seccomp profile admitting `unshare` and `clone` with `CLONE_NEWUSER|CLONE_NEWNET`. `RuntimeDefault` does not admit it (Context), so under PodSecurity `restricted` the second is a `Localhost` profile installed on every node. Meeting the sysctl alone leaves every `NoNetwork` Exec refused. It separates the agent's volume by the mount, under any uid, which is what #966 lacked: on `garam-dev` the shared account owned the agent's store on a volume both containers mounted, and an Exec child read and appended to it. It keeps secrets out of the child by absence (ADR 0003) and by the workspace marking itself non-dumpable, so a same-uid child can neither read its environment nor attach to it. **It does not separate the child from the workspace process.** The child runs as the workspace's own uid, so it reads and writes whatever that uid can — the workspace's config file among it, whose owner-only mode holds against other uids and not this one — and **it can signal the workspace server, stopping the data plane — Read, Write, List and Exec alike — until the container restarts.** `RLIMIT_NPROC` does not bind there, because it counts every process of a shared uid; the container's process limit is the bound.
- Any other combination fails closed: an unprivileged process with an exec UID other than its own reports `agent_uid unavailable`. A shape that mounts the agent's volume into the workspace container while the child runs as the uid owning the store is unsupported in either shape, because nothing then separates the child from the store.
- The privileged drop needs a capability set, not just privilege: `SETUID`/`SETGID` for the credential drop, `CHOWN` for the workspace-directory handover, `SYS_ADMIN` for the netns unshare, and `KILL` for the deadline. `deployment.md` §Capabilities holds the operator-facing table and what dropping each one costs.
- Exec children share the workspace directory's ownership story: a privileged workspace chowns the workspace directory to the exec UID, keeps the directory's write bit for its own group, and gives every file the gRPC contract writes to the same UID — so files written by tools through the gRPC contract and by exec'd children share one owner, without the workspace holding a capability over every file in its container.
- The unauthenticated Exec listener is a remote shell into the workspace, so the loopback-only fail-closed posture (ADR 0012) is what stands until contract authentication exists.

## Rejected alternatives

- **Typed compute tools only (`jq_query`, `python_eval`)** — narrow but every new use case needs a new tool; exec is the general answer.
- **Keep no exec capability** — simplest, but the workloads that need exec are real.
- **Support the privileged drop only, and leave `restricted` deployments without a supported shape** (#1049, option A). Consumers would move every agent namespace to a weaker Pod Security Standard and grant a root container `SYS_ADMIN`, which the `restricted` consumer judged a wider, node-level exposure than the in-workspace boundary it buys; it declined. The privileged drop stays supported for the consumer that runs it.
- **Support the unprivileged shape by raising `user.max_user_namespaces` alone, leaving the shape unsupported** (#1049). The sysctl does not make `NoNetwork` Exec work under `RuntimeDefault`, which refuses the clone first (Context), and the shape would still be one the documents disown. Support needs every condition above stated, which is what makes the sysctl and the seccomp profile requirements of a supported shape rather than a workaround.
- **Exec in the agent process** — splits the computer in two: the agent would need the workspace's files at an identical local path (a shared-mount trick) for exec'd programs to see them, and the agent container would carry the shell, the privileges, and the untrusted-code surface the pod split exists to keep out of it (ADR 0017).
