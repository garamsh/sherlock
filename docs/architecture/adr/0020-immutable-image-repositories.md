# ADR 0020: The image repositories are immutable, and a consumer references an image by digest

> Status: accepted
> Date: 2026-08-24 (revised in place 2026-08-24; 2026-08-24; 2026-09-05; 2026-09-06; 2026-09-25; 2026-10-09; 2026-10-09; 2026-10-09)

## Context

sherlock publishes two images, built from `build/agent.Dockerfile` and `build/workspace.Dockerfile`, into ECR repositories in an AWS account this repository does not own and cannot read: `garam/sherlock-agent` and `garam/sherlock-workspace` hold what a release publishes (semver tag) and nothing else, and `garam-dev/sherlock-agent` and `garam-dev/sherlock-workspace` hold what development builds push (commit short SHA). Until 2026-10-09 both kinds went to the two `garam/` repositories and were told apart by tag; the owner then directed, for every project in that account, that development builds go to a path of their own. The path's name is the last of four decisions the owner made, in this order: `garam-dev/` (garam PM session record `d419803e-0907-4cd0-868f-cd4296d455bf`, 2026-10-09T00:21+09:00); `dev/`, asked by `garamsh/infra` which name to use (garamsh/infra session record `bf98e13d-e7c9-4995-826b-39696b4021df`, 2026-10-09T00:23:20+09:00); `dev/` again, asked by infra to choose between `garam-dev/` and `dev/` (same record, 2026-10-09T00:32:59+09:00); and `garam-dev/`, typed by the owner as "dev가 아니라 garam-dev" (garam-dev, not dev; same record, 2026-10-09T06:53:15+09:00). The latest governs (#985, #990); `deployment.md` §Images and tags quotes each and gives its line in the record. The agent image carries the first-party tool executables at `/opt/sherlock/tools/<name>/` (ADR 0021); a separate `sherlock/tools` image was published through 2026-09-25 and is no longer built or pushed from this date. The decision below binds those four and no others — `garam/garam-agent-operator` and `garam/garam-agent-operator-control` share the namespace and are the operator's, not sherlock's (`aws ecr describe-repositories --region ap-northeast-2`, read 2026-10-09T01:29+09:00; the `garam/gagent-operator` and `garam/gagent-operator-dev` this record named before are not in the account). What that account holds is `garamsh/infra`'s to set. What sherlock requires of it is this project's to state, and `deployment.md` had been stating it as a description of three settings — immutability, scan-on-push and a lifecycle policy — rather than as a requirement. One of the three was already false when the description was read: `garamsh/infra` declares no lifecycle policy on any repository in that account and records the absence as a deliberate open question rather than an oversight (reported by the garam PM, 2026-08-23).

That description was load-bearing while it lasted. `garamsh/infra` planned a mutability flip across five ECR repositories, read `IMMUTABLE` here, and restructured the change so each application states its own repository setting instead (2026-08-23). It did that work by being accurate on the day it was read, which is what a description of another project's account cannot be relied on to stay.

What makes immutability a requirement rather than a preference is in this repository. `REVISION` is the checked-out commit and marks no dirty tree, and both Dockerfiles carry it into `org.opencontainers.image.revision` while the recipe carries it into the tag — so an image built from a tree that had moved past that commit still reads as the commit's own, in its label and in its name. `make build-images` refuses to make one where that revision is the git default: it compares what docker reads — the build contexts, the Dockerfiles it is handed, and the ignore file that decides what each context holds — against the commit, and names the paths that differ (#696, #698). The refusal is scoped to the default because an explicit `REVISION=` is a claim its author is making, so a mislabelled image stays something a person can build deliberately and nothing in the artifact marks it as one. What bounds it from there is the repository refusing the second push of a tag.

## Decision

**Every sherlock image repository is created `IMMUTABLE` and is never made mutable; a tag in one names a single commit and never moves; sherlock requires neither a lifecycle policy nor image scanning; and a consumer references an image by digest with `imagePullPolicy: Always`.**

### Immutable, dev and production alike

This holds for the `garam-dev/` repositories as for the `garam/` ones. The owner's directive moved development builds to their own path and said nothing about their mutability, so the rules this record sets for the release path carry over unchanged — and the argument below is strongest on the development path, where builds are pushed by hand.

Push a dirty-tree build under a tag some clean build already holds, and a mutable repository takes it: the overwrite is silent, and the tag now names a commit whose tree was not what was built. An immutable repository refuses it: ECR's `PutImage` answers `ImageTagAlreadyExistsException`. Immutability converts a silent mislabel into a refused push, which is the shape ADR 0010 requires of the executor — it never silently upgrades, because a capability reported unavailable is better than a change nobody sees.

The second reason is that the setting is retroactive. Tag immutability is a property of the repository and not of a tag, and ECR records nothing about the policy a tag was pushed under, so a repository that is ever mutable leaves every tag it holds a readable label rather than an identifier — the ones pushed while it was immutable included (from the gitops PM, 2026-08-23). A tag identifies a build here only because these repositories have never been mutable, which makes this a requirement on their creation and not only on their present setting.

### A tag names one commit and never moves

This follows from immutability rather than standing beside it: a moving tag cannot exist in a repository that refuses a second push of a name. There is no `:dev` and no `:latest`; the only tags sherlock pushes are a semver (`0.1.0`, ...) to `garam/` for a release and the commit short SHA to `garam-dev/` for a development build. With the two kinds in separate paths, the tag no longer has to say which kind a build is, and it still says which commit.

The release scheme `deployment.md` §Images and tags records is such a tag — a `v`-prefixed git tag becomes the image tag without the `v` — so re-pointing that git tag and releasing again is refused rather than silently overwritten.

### Neither a lifecycle policy nor image scanning is required

The clause claiming a lifecycle policy is removed rather than made true. The semver tags (production) hold released versions, where expiry is the wrong behaviour, and the commit-SHA tags (development) hold build outputs that are not released versions for it to act on. Scan-on-push goes the same way and for the same reason rather than for a judgement about scanning: sherlock has no requirement to state about it, and what it had was a description of the account. Either control the account runs for its own hygiene is `garamsh/infra`'s to decide; sherlock depends on neither and describes neither.

### A consumer references the digest and pulls always

A tag's stability rests on a repository setting that can be changed retroactively, and a consumer cannot check from outside that it never was. So the reference is the digest and the tag is what a human reads. That is not in tension with requiring the tag to identify a build: sherlock requires it of its own repositories, and a consumer who cannot verify the requirement was kept does not rest on it.

`imagePullPolicy: Always` for a reason specific to these repositories rather than as a general preference. Immutability fixes what a tag resolves to and promises nothing about the tag continuing to exist, so the failure to be loud about is a reference that stops resolving. The default `IfNotPresent` turns that into a per-node stale-cache fault that presents as the node's; `Always` makes it uniform and immediate.

## Consequences

- **A reader who cannot see the account can act on `deployment.md` §Images and tags, and a reviewer can check it against the account.** The requirements there state what the repositories owe this project, and none of them goes stale when a setting changes, because none describes a setting. That property belongs to the requirements and not to the whole section: since the release path was built, the section also records what that account held when someone with access read it — what the repositories hold, and what the push role has done — and that half carries its reading date for exactly the reason this record distrusts descriptions.
- **Immutability bounds the dirty-tree failure, and the build no longer produces one by default.** The repository's refusal fires on the *second* push of a name, so a first push of a mislabelled image would still succeed and read as clean — `REVISION` marks no dirty tree either way. What can still produce one is narrow and named: a build passing its own `REVISION=`, which the guard exempts because a stated revision is a claim its author made, and a change to something the build does not read. The `Makefile` that invokes docker is outside the check deliberately — a guard that refused the build of its own repair is what gets overridden rather than obeyed (#695) — while everything docker itself reads is inside it (#698).
- **The tag is derived, and the local build pushes nothing.** `make build-images` tags each image with the same `REVISION` its revision label carries, so a tag cannot name one commit while the label names another, and there is no `:latest` for an immutable repository to take once and refuse after (#693). What pushes is the release path, and it exists — a workflow and the OIDC-assumed role it publishes through (`deployment.md` §Images and tags) — so the rule these repositories are created under binds that workflow rather than falling on whoever pushes first. It has bound three releases: release runs 37237000323, 37257028964 and 37508695410 pushed `0.1.0`, `0.2.0` and `0.2.1` to the production two, each under the workflow's role. The first push to those repositories was still a person's: the `837b80afe272` pair, a development build pushed by hand on 2026-09-27 before any release run, is the one pair there the workflow did not push. `deployment.md` §Images and tags carries the record and the reading each row rests on; nothing here re-checks it.
- **Nothing here enforces what the repositories must be**, which is why it is stated as a requirement. This repository cannot read that account and does not try, so immutability and its retroactive reach bind whoever creates the repositories and are checkable only there. One obligation has since acquired a partial enforcer: the release workflow is the only pusher this repository holds, and no moving tag can reach these repositories through it, because the name it publishes is derived from the git tag that triggered it. That reaches its own pushes and nothing else, and a hand push to the same repositories is subject to none of it.
- **A bad image at a taken tag is replaced by a new tag, never overwritten.** That cost is accepted: it is the same refusal the record is chosen for.
- **The account's own hygiene is unconstrained by this record.** It states what sherlock requires, not what the account may hold, so a lifecycle or scanning policy `garamsh/infra` adds for reasons of its own contradicts nothing here and needs no change to this document.

## Rejected alternatives

- **Making the description true** — adding the lifecycle policy so the sentence holds. It leaves a description of another project's account in this document, free to go stale again with nothing here able to notice. The false clause was the visible instance; the form was the defect (#690).
- **`MUTABLE` repositories with digest-pinned consumers.** A consumer that references the digest is unharmed by a moved tag, so mutability would cost it nothing. Rejected for what it costs elsewhere: the tag stops naming a build for anyone who reads one, and a silent overwrite is the failure on this path that leaves no trace. The build-time guard refuses the mislabelled image a second push would carry, but only where the revision is the default, and nothing in this repository reaches what a registry does with a tag it already holds.
- **One path for both kinds, classified by tag** — development builds tagged by commit beside the releases in `garam/`, the scheme until 2026-10-09. Replaced by the owner's directive that development builds go under a path of their own in every project of that account, named `garam-dev/` (#985, #990); a reader of `garam/` now finds releases alone, and the release workflow's grant, which names only the `garam/` repositories, reaches none of the development path.
- **`dev/` as the development path** — the owner's interim choice, made at 2026-10-09T00:23:20+09:00 and again at 00:32:59+09:00, when the option infra put to the owner argued that the cluster is named `garam-dev`, so `garam-dev/` would make one string mean the cluster in one place and development in another within the same account. Superseded by the owner's decision at 2026-10-09T06:53:15+09:00, `garam-dev/`, which is later and governs. garamsh/infra reports destroying the two `dev/sherlock-*` repositories made under the interim choice; `deployment.md` §Images and tags records that reading and its source.
- **A moving development tag (`dev`).** It cannot exist in an immutable repository, and the argument for immutability is strongest exactly there, where dirty-tree builds are most likely.
- **`imagePullPolicy: IfNotPresent`, the orchestrator's default.** It turns a reference that stopped resolving into a per-node stale-cache fault that presents as the node's.
- **Querying the account to settle what it currently holds.** The required form does not depend on what is there, so the answer would change nothing — and it is not this repository's account to inspect.
