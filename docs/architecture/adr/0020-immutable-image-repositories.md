# ADR 0020: Each image is published to one immutable repository, and a consumer references an image by digest

> Status: accepted
> Date: 2026-08-24 (revised in place 2026-08-24; 2026-08-24; 2026-09-05; 2026-09-06; 2026-09-25; 2026-10-09; 2026-10-09; 2026-10-09; 2026-10-09; 2026-10-28)

## Context

sherlock publishes two images, built from `build/agent.Dockerfile` and `build/workspace.Dockerfile`, into ECR repositories in an AWS account this repository does not own. Two things are settled outside this repository and bind it:

- **The name.** A repository is named `<publishing repository>/<image>`, and the image name never repeats the prefix (garamsh/aurora ADR 0033, "A repository in `image_publishers` is named `<publishing repository>/<image>`", at `90d9ba9921f27eccb2f517f487cbb74ad412e0bd`; garamsh/aurora#710). The image names are this project's to choose, and it chose `agent` and `workspace` (#1170).
- **One repository per image.** The owner decided on 2026-10-28 that there is no separate development path: an image has one repository, release and development builds alike, and the `garam-dev/` namespace goes away (garamsh/aurora#711, relayed by garam's PM and confirmed by the owner in this project's PM session the same day, as #1170 records).

The decision below binds every repository this project publishes an image to, and it is scoped by that property rather than by a list of what the account holds. Which repositories those are is named in this repository, where a reviewer can check it: `.github/workflows/release.yml` pushes to them, and `deployment.md` §Images and tags names them for a hand push. A repository nothing here publishes to is not this record's, whoever owns it. What the account holds is the account owner's to set (garamsh/aurora). What sherlock requires of the repositories it publishes to is this project's to state, as requirements and not as a description of settings — a description of another project's account goes stale with nothing here able to notice. `deployment.md` once described three settings — immutability, scan-on-push and a lifecycle policy — and one of the three was false when it was read: the account declared no lifecycle policy on any repository (reported by the garam PM, 2026-08-23).

That description was load-bearing while it lasted. The account's owner, then `garamsh/infra`, planned a mutability flip across five ECR repositories, read `IMMUTABLE` here, and restructured the change so each application states its own repository setting instead (2026-08-23). It did that work by being accurate on the day it was read, which is what a description of another project's account cannot be relied on to stay.

What makes immutability a requirement rather than a preference is in this repository. `REVISION` is the checked-out commit and marks no dirty tree, and both Dockerfiles carry it into `org.opencontainers.image.revision` while the recipe carries it into the tag — so an image built from a tree that had moved past that commit still reads as the commit's own, in its label and in its name. `make build-images` refuses to make one where that revision is the git default: it compares what docker reads — the build contexts, the Dockerfiles it is handed, and the ignore file that decides what each context holds — against the commit, and names the paths that differ (#696, #698). The refusal is scoped to the default because an explicit `REVISION=` is a claim its author is making, so a mislabelled image stays something a person can build deliberately and nothing in the artifact marks it as one. What bounds it from there is the repository refusing the second push of a tag.

## Decision

**Each image sherlock builds is published to one repository, `sherlock/<image>` — `sherlock/agent` and `sherlock/workspace` — which holds its releases and its development builds alike, told apart by tag pattern; every repository sherlock publishes to is created `IMMUTABLE`, with no tag-mutability exclusion, and is never made mutable; a tag names a single commit and never moves; sherlock requires neither a lifecycle policy nor image scanning; and a consumer references an image by digest with `imagePullPolicy: Always`.**

### One repository per image, two tag patterns

A release tag is a semver, `X.Y.Z` (`0.1.0`, ...). A development tag is the commit's short SHA (`837b80afe272`). The two patterns cannot meet: a semver holds two dots and a short SHA holds none, so a reader, a policy or a consumer selecting by pattern tells a release from a development build without a second path to do it. A release tag is pushed only by the release workflow, which derives it from the git tag that triggered it; a development tag is pushed by hand.

### Immutable, releases and development builds alike

Both kinds sit in one repository, so the rules below hold for both — and the argument is strongest for development builds, which are pushed by hand.

Push a dirty-tree build under a tag some clean build already holds, and a mutable repository takes it: the overwrite is silent, and the tag now names a commit whose tree was not what was built. An immutable repository refuses it: ECR's `PutImage` answers `ImageTagAlreadyExistsException`. Immutability converts a silent mislabel into a refused push, which is the shape ADR 0010 requires of the executor — it never silently upgrades, because a capability reported unavailable is better than a change nobody sees.

The second reason is that the setting is retroactive. Tag immutability is a property of the repository and not of a tag, and ECR records nothing about the policy a tag was pushed under, so a repository that is ever mutable leaves every tag it holds a readable label rather than an identifier — the ones pushed while it was immutable included (from the gitops PM, 2026-08-23). A tag identifies a build here only because these repositories have never been mutable, which makes this a requirement on their creation and not only on their present setting.

So the setting is plain `IMMUTABLE`, with no tag-mutability exclusion. sherlock pushes no moving tag, so an exclusion buys it nothing. And an exclusion filter is itself a repository setting that can be changed later: whatever pattern it comes to match, the tags under that pattern become labels retroactively, which is the argument above reopened.

### A tag names one commit and never moves

This follows from immutability rather than standing beside it: a moving tag cannot exist in a repository that refuses a second push of a name. There is no `:dev` and no `:latest`; the only tags sherlock pushes are the two patterns above, and either is taken once and refused on a second push.

The release scheme `deployment.md` §Images and tags records is such a tag — a `v`-prefixed git tag becomes the image tag without the `v` — so re-pointing that git tag and releasing again is refused rather than silently overwritten.

### Neither a lifecycle policy nor image scanning is required

The clause claiming a lifecycle policy is removed rather than made true. The semver tags hold released versions, where expiry is the wrong behaviour, and the commit-SHA tags hold build outputs that are not released versions for it to act on. Scan-on-push goes the same way and for the same reason rather than for a judgement about scanning: sherlock has no requirement to state about it, and what it had was a description of the account. Either control the account runs for its own hygiene is the account owner's to decide; sherlock depends on neither and describes neither.

### A consumer references the digest and pulls always

A tag's stability rests on a repository setting that can be changed retroactively, and a consumer cannot check from outside that it never was. So the reference is the digest and the tag is what a human reads. That is not in tension with requiring the tag to identify a build: sherlock requires it of its own repositories, and a consumer who cannot verify the requirement was kept does not rest on it.

`imagePullPolicy: Always` for a reason specific to these repositories rather than as a general preference. Immutability fixes what a tag resolves to and promises nothing about the tag continuing to exist, so the failure to be loud about is a reference that stops resolving. The default `IfNotPresent` turns that into a per-node stale-cache fault that presents as the node's; `Always` makes it uniform and immediate.

## Consequences

- **A reader who cannot see the account can act on `deployment.md` §Images and tags, and a reviewer can check it against the account.** The requirements there state what the repositories owe this project, and none of them goes stale when a setting changes, because none describes a setting. That property belongs to the requirements and not to the whole section: the section also records what that account held when someone with access read it — what the repositories held, and what the push role has done — and that half carries its reading date for exactly the reason this record distrusts descriptions.
- **The scope cannot go stale with the account.** It names a property — the repositories this project publishes to — and the instance of it is `.github/workflows/release.yml`, which a reviewer reads in this repository. A repository created, renamed or retired in the account changes nothing here until this project publishes to it.
- **Immutability bounds the dirty-tree failure, and the build no longer produces one by default.** The repository's refusal fires on the *second* push of a name, so a first push of a mislabelled image would still succeed and read as clean — `REVISION` marks no dirty tree either way. What can still produce one is narrow and named: a build passing its own `REVISION=`, which the guard exempts because a stated revision is a claim its author made, and a change to something the build does not read. The `Makefile` that invokes docker is outside the check deliberately — a guard that refused the build of its own repair is what gets overridden rather than obeyed (#695) — while everything docker itself reads is inside it (#698).
- **The tag is derived, and the local build pushes nothing.** `make build-images` tags each image with the same `REVISION` its revision label carries, so a tag cannot name one commit while the label names another, and there is no `:latest` for an immutable repository to take once and refuse after (#693). What pushes a release is the release workflow and the OIDC-assumed role it publishes through (`deployment.md` §Images and tags), so the rule these repositories are created under binds that workflow rather than falling on whoever pushes first. `deployment.md` §Images and tags carries the record of what each release pushed and the reading each row rests on; nothing here re-checks it.
- **The path no longer keeps the two kinds apart; the tag pattern does.** The release workflow's grant reaches the development tags in the same repository, and a hand push reaches the release names. The workflow pushes only the semver it derives from its git tag, and a hand push takes a short SHA only — a semver pushed by hand takes a release name nobody can take back.
- **Nothing here enforces what the repositories must be**, which is why it is stated as a requirement. Nothing in this repository reads that account, so immutability and its retroactive reach bind whoever creates the repositories and are checkable only there. One obligation has a partial enforcer: the release workflow is the only pusher this repository holds, and no moving tag can reach these repositories through it, because the name it publishes is derived from the git tag that triggered it. That reaches its own pushes and nothing else, and a hand push to the same repositories is subject to none of it.
- **A bad image at a taken tag is replaced by a new tag, never overwritten.** That cost is accepted: it is the same refusal the record is chosen for.
- **The account's own hygiene is unconstrained by this record.** It states what sherlock requires, not what the account may hold, so a lifecycle or scanning policy the account owner adds for reasons of its own contradicts nothing here and needs no change to this document.

## Rejected alternatives

- **Making the description true** — adding the lifecycle policy so the sentence holds. It leaves a description of another project's account in this document, free to go stale again with nothing here able to notice. The false clause was the visible instance; the form was the defect (#690).
- **Scoping the decision by an inventory of the account** — naming the repositories it binds, as this record did until 2026-10-28. The inventory set the decision's scope and was a description of an account this repository does not read, so it went stale with nothing here to notice: two of the five repositories it once named had been removed when it was next read (#793). The property it is scoped by now is true whatever the account holds.
- **`MUTABLE` repositories with digest-pinned consumers.** A consumer that references the digest is unharmed by a moved tag, so mutability would cost it nothing. Rejected for what it costs elsewhere: the tag stops naming a build for anyone who reads one, and a silent overwrite is the failure on this path that leaves no trace. The build-time guard refuses the mislabelled image a second push would carry, but only where the revision is the default, and nothing in this repository reaches what a registry does with a tag it already holds.
- **A development path of its own** — development builds in `garam-dev/sherlock-<image>` beside the releases in `garam/sherlock-<image>`, the scheme from 2026-10-09 to 2026-10-28 (#985, #990). Replaced by the owner's decision that an image has one repository and the `garam-dev/` namespace goes away (garamsh/aurora#711, #1170); the tag patterns, which cannot meet, tell the two kinds apart without it.
- **A moving development tag (`dev`).** It cannot exist in an immutable repository, and the argument for immutability is strongest exactly there, where dirty-tree builds are most likely.
- **`imagePullPolicy: IfNotPresent`, the orchestrator's default.** It turns a reference that stopped resolving into a per-node stale-cache fault that presents as the node's.
- **Querying the account to settle what it currently holds.** The required form does not depend on what is there, so the answer would change nothing — and it is not this repository's account to inspect.
