# Agent

Governs the agent: the reasoning loop, memory, tool use, and model access. Rationale: ADR 0017, ADR 0009, ADR 0004, ADR 0006.

## Current decisions

- The agent is the self: one continuous rolling session per agent, running in its own container (ADR 0017). Its organs:
  - **Gateway** — the ears and eyes; message ingress and the monitoring stream (governed by `gateway.md`).
  - **Reasoning loop** — model call, tool-call decision, result incorporation, repeat.
  - **Memory** — the long-term organ; a layer, never a tool (governed by `memory.md`).
  - **Mouth** — outbound messaging; the agent's own speech to channels and peers (the `message_send` tool, ADR 0017).
  - **Hands** — the platform tool client (`internal/tool`): reads tool manifests from the operator's `tools/` directory, spawns each tool's executable, validates inputs and outputs at the boundary against the manifest's JSON Schemas, and holds each manifest's hash against the operator's pin set at startup, refusing a tool that drifted from its pin or that the set does not name (ADR 0017, ADR 0009). The pin set is the operator's, through config; an agent configured without one loads unpinned and says so at startup. There is no compile-time registry, no runtime plugin loader, no wire protocol, no remote tool registry.
- Tools are scripts with manifests (ADR 0017, ADR 0009). The platform specifies only the contract shape and the call protocol; the tool owns its description, its validation, and its behavior. The operator's `tools/` directory is the installation boundary: a tool is present if and only if the operator dropped its directory, and the platform validates required tools at startup (a missing required tool fails closed).
- Process exec is the workspace's capability (ADR 0017), surfaced to the model as the `shell_exec` tool — an independent tool server calling the workspace's Exec RPC (ADR 0008). The agent executes nothing: the shell_exec tool calls the workspace gRPC client, and the workspace runs the command in its own directory dropped to the configured exec UID, so exec'd programs see the same files the file tools serves.
- The reasoning loop is unchanged in shape; what changed is where tools come from. The loop as implemented today is restated below.
- Model requests carry JSON Schemas for tools and terminal writeback, with constrained decoding requested where supported. Endpoint acceptance is not proof that generated arguments conform; the runtime parses the fields it owns and rejects invalid updates. The terminal response carries the visible reply, a current-work update and the turn's fact writes (ADR 0018).

## Current state (the loop as implemented)

- The session owns one durable current-work record (ADR 0006): exact source and the current arrival govern one lifecycle status and subordinate progress. Initial source is unconditional; later arrivals are retained by default without numeric selection or transcription. Curation can dismiss the current neutral arrival or replace prior source for new work. Interrupted arrivals are retained before another arrives. Reasoning receives the record independently of compaction; fact recall receives only the current turn's task.
- Nonterminal effects need persisted intent and an individual attempt, without a compulsory summary call. Idle work becomes active on an attempt. Canceled and completed status prohibit every operator call before dispatch and every status change until a replacement arrival with active status is saved. Progress cannot reopen work. The model still interprets whether a replacement actually carries new authorization.
- A fresh idle fact-only source retires with its progress after its own successful fact writeback and no attempted effects; later facts cannot retire older source. Replacement clears prior source and stale progress, while unretired attempts survive. Unknown or failed attempts block completion until individually reconciled; successful returns may remain as evidence. Terminal work cannot use tools to inspect uncertainty without new authorization. Retained arrivals and attempts remain unbounded; failed curation may retain neutral traffic until replacement.
- Checkpoints acknowledge the model through a matched tool result. A failed turn resets volatile history before the next turn reloads durable work, avoiding unanswered calls after a failed persistence boundary. Startup executes no pending tool calls. Free product coverage in `tests/working_context_test.go` establishes these boundaries, not model competence.

- One rolling session per agent process; each turn follows the memory lifecycle: frame, recall, act, writeback. Recall is a model call in front of the store, because an addressed store answers nothing asked in words (ADR 0018, ADR 0019): it resolves the task into an address, reads it, and widens to the subject where that address held nothing. The turn emits one recall event carrying which of those it did.
- Two per-turn guards keep a stalled model from consuming the iteration budget: an identical-failed-call guard (same name, input, and error three times) and a per-tool call budget (six per turn); each substitutes a synthetic result and emits a failed `tool_call` event, and the iteration cap remains the backstop.
- The agent's tool set is built at startup from the operator's tool list. The `message_send` tool is required; tools that need the workspace (file_read, file_write, file_list, shell_exec) hold the workspace gRPC client themselves. The tool surface the model sees is the JSON Schema descriptors each manifest declares, re-validated at the boundary, projected into the accepted subset where a provider's API constrains the shape — the OpenAI provider's strict mode has no optional property, so it promotes each one to required and nullable at the wire. The projection is the provider's and stops there: the boundary keeps holding calls to the manifest, reading the null that promotion invites as the absence the manifest already permits.
- Memory is a layer, never an operator tool: the read-only memory search tool is gone, and reads reach the store through the lifecycle (ADR 0011, ADR 0017). The writeback travels as a reserved tool call, and that is not the thing ADR 0017 forbids — it is the platform's, not the operator's. The session adds the descriptor to what the model is shown, intercepts the call, never routes it to the tool client, and drops an operator tool that takes the reserved name rather than letting it shadow. The model can see it because a tool it cannot see is one it cannot call; it cannot decline it, because a turn does not end without it (issue #615).
- **A turn that does not write does not finish.** A model response carrying neither the writeback nor a tool call is not terminal: the session says what is missing and asks again, and a model that never complies exhausts the act loop and fails the turn. A dropped writeback was a warn while the turn still succeeded (issue #93), which is what made a provider ignoring the response format look like a turn that stated no facts; the reply and the facts now arrive in the same call, so there is nothing to hand back when it is missing or malformed.
- All model access goes through one consumer-owned interface, and which wire protocol implements it is configuration (ADR 0004): `mock` is the scripted model that keeps the full pipeline runnable offline (it exercises `shell_exec`, then `message_send`, then a memory write — the full tool surface), `openai-compatible` speaks chat-completions and `anthropic-compatible` speaks the Messages protocol, with the base URL picking the endpoint speaking the named one. Memory needs no model of its own since #582 removed the embedder: an addressed store computes where a fact is.
- Instructions compose an operator-owned ego file (`--ego-file`, flag-only) with the platform contract (`agent.Contract`), which is never overridable, so a custom prompt cannot break the memory loop. The contract's writeback section is the prose half of the reserved writeback tool's parameters; the reserved call is the turn's only ending, the contract what asks the model to fill it (ADR 0011, issue #615).

## Open questions

- Whether the `anthropic-compatible` client and the live Messages API agree. The client is written to the protocol's documented contract and tested against a local fake, and no request has yet gone to the real endpoint, so the tests establish what the client sends and not what the API accepts (`README.md` §Endpoints, and how far each is verified). The first live call is what settles it.
- Progressive disclosure for large tool sets (a `search_tools`-style tool that returns descriptors on demand) — when the operator's tool list first warrants it.
