# Agent

Governs the agent: the reasoning loop, memory, tool use, and model access. Rationale: ADR 0017, ADR 0009, ADR 0004, ADR 0006, ADR 0011, ADR 0019, ADR 0024, ADR 0029.

## Current decisions

- The agent is the self: one continuous rolling session per agent, running in its own container (ADR 0017). Its organs:
  - **Gateway** — the ears and eyes; message ingress and the monitoring stream (governed by `gateway.md`).
  - **Reasoning loop** — model call, tool-call decision, result incorporation, repeat.
  - **Memory** — the source-linked conversation organ, whose search and inspection calls are reserved inside the agent (governed by `memory.md`).
  - **Mouth** — outbound messaging; the agent's own speech to channels and peers (the `message_send` tool, ADR 0017).
  - **Hands** — the platform tool client (`internal/tool`): reads tool manifests from the operator's `tools/` directory, spawns each tool's executable, validates inputs and outputs at the boundary against the manifest's JSON Schemas, and holds each manifest's hash against the operator's pin set at startup, refusing a tool that drifted from its pin or that the set does not name (ADR 0017, ADR 0009). The pin set is the operator's, through config; an agent configured without one loads unpinned and says so at startup. There is no compile-time registry, no runtime plugin loader, no wire protocol, no remote tool registry.
- Tools are scripts with manifests (ADR 0017, ADR 0009). The platform specifies only the contract shape and the call protocol; the tool owns its description, its validation, and its behavior. The operator's `tools/` directory is the installation boundary: a tool is present if and only if the operator dropped its directory, and the platform validates required tools at startup (a missing required tool fails closed).
- Installing a tool trusts it with the agent environment whole, including every credential the agent holds (ADR 0009, ADR 0017, `security.md`). The tool client provides no per-tool credential scope and dispatches no secrets; a tool cannot hold a credential the agent does not.
- Process exec is the workspace's capability (ADR 0017), surfaced to the model as the `shell_exec` tool — an independent tool server calling the workspace's Exec RPC (ADR 0008). The agent runs no exec'd command — the only processes it starts are the installed tool executables (ADR 0021): the shell_exec tool calls the workspace gRPC client, and the workspace runs the command in its own directory dropped to the configured exec UID, so exec'd programs see the same files the file tools serves.
- The reasoning loop is unchanged in shape; what changed is where tools come from. The loop as implemented today is restated below.
- Provider tool schemas constrain the reserved terminal response, memory search and memory inspection calls when the provider supports that mode. The terminal response carries the reply and the agent's note; the addressed `memory_ops` field is gone (ADR 0011).

## Current state (the loop as implemented)

- One rolling session per agent process. Each turn leads with the instructions and the saved note, frames the current task, recalls bounded older summaries by embedding similarity and an entity walk, acts with recent context, and ends through the reserved response call. The runtime restores recent visible messages from SQLite on restart, and the note from the same file (ADR 0006, ADR 0011, ADR 0019).
- Two per-turn guards keep a stalled model from consuming the iteration budget: an identical-failed-call guard (same name, input, and error three times) and a per-tool call budget (six per turn); each substitutes a synthetic result and emits a failed `tool_call` event, and the iteration cap remains the backstop.
- The agent's tool set is built at startup from the operator's tool list. The `message_send` tool is required; tools that need the workspace (file_read, file_write, file_list, shell_exec) hold the workspace gRPC client themselves. The tool surface the model sees is the JSON Schema descriptors each manifest declares, re-validated at the boundary, projected into the accepted subset where a provider's API constrains the shape — the OpenAI provider's strict mode has no optional property, so it promotes each one to required and nullable at the wire. The projection is the provider's and stops there: the boundary keeps holding calls to the manifest, reading the null that promotion invites as the absence the manifest already permits. The file and GitHub capabilities ship as one tool per operation with only required inputs, because a model offered nullable fields has nulled all of them (`environment.md` §File operation contracts, §GitHub operation contracts).
- Memory search and memory inspection are reserved agent calls, not operator-installed tools. The session intercepts them. `memory_search` takes mid episodes similar to a query the model writes and ones an entity walk reaches from the names in it, in turn, at most five per call (ADR 0019); `memory_inspect` reads exact visible source messages from an episode's interval (ADR 0018). An operator tool with a reserved name is dropped with a warning. The terminal response call is reserved in the same way.
- **A turn without the reserved terminal response does not finish.** The session asks again if a model stops without the call, and hands a note past 2,000 characters back to the model as the call's result; arguments that are not JSON fail the turn. A successful reply and its visible task are persisted, then the note, before the terminal event (ADR 0011).
- Chat model access goes through one consumer-owned interface and embedding through a second (ADR 0004). Mid-episode synthesis uses the session model; recall makes no model call and uses the embedder configured in the `embedding:` section. `mock` remains the offline scripted stand-in, with an offline embedder beside it, and configured OpenAI- or Anthropic-compatible clients supply the live chat endpoint beside an OpenAI-compatible embeddings endpoint. The mock answers a request offering `memory_summary`, which only synthesis offers, with one fixed valid call outside its turn script, so a mock agent's batches synthesize.
- The chat model's key comes from the variable `model.api-key-env` names, read once at startup, or from the file `model.api-key-file` names, which the platform rewrites and the client reads for every request (ADR 0029). Naming both fails startup. A file the process cannot read fails startup, and one that becomes unreadable later fails the model call with an error naming the file, not the agent. A request answered with 401 under the file reads it once more and is sent once more, and a second 401 fails the call; a key from the variable is never retried. The embedder keeps its own `embedding.api-key-env`.
- **Each turn mints one identifier, and every model request of the turn carries it** in the header `X-Turn-Id` — the loop's calls, a retried call and the mid-episode synthesis inside the turn alike — so an endpoint that chooses a model per turn can keep the turn on it (ADR 0029). The identifier is opaque random hex, and a request outside a turn carries none.
- Instructions compose the operator ego (or the embedded default when none is named), then the operator instructions when an instructions file is named, then the platform contract, followed by the saved note under "Your note" (ADR 0024). The operator instructions add to the ego rather than replace it, and with none named the instructions are exactly the ego and the contract. The contract is never overridden by either operator file; it tells the model to search with a standalone query when recall misses, to inspect sources for exact wording, to treat a retrieved candidate as a lead, not an established answer, and to restate its whole note in every terminal call.

## Open questions

- Whether the `anthropic-compatible` client and the live Messages API agree. The client is written to the protocol's documented contract and tested against a local fake, and no request has yet gone to the real endpoint, so the tests establish what the client sends and not what the API accepts (`README.md` §Endpoints, and how far each is verified). The first live call is what settles it.
- Whether garam's AI gateway reads the turn identifier under the name `X-Turn-Id`. Sherlock proposed it on garamsh/garam#1704, and garam has not confirmed it there; a different name is a change to `agent.TurnIDHeader` (ADR 0029).
- Progressive disclosure for large tool sets (a `search_tools`-style tool that returns descriptors on demand) — when the operator's tool list first warrants it.
