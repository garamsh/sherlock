# Deployment

Governs what has to be true to run this workload as a pod: the two processes, what they bind, what they mount, what kills them at boot, what an orchestrator must allow on shutdown, and how an agent's stored state is copied and restored. The architecture behind it is `environment.md` and `security.md`; this file states the operator-facing consequences and does not restate them. Rationale: ADR 0017, ADR 0012, ADR 0008, ADR 0010, ADR 0003, ADR 0020, ADR 0002, ADR 0022, ADR 0024, ADR 0025.

## The two processes

One pod per agent, two containers (ADR 0017). Both are the same binary under different subcommands.

| | agent container | workspace container |
|---|---|---|
| Command | `sherlock agent` | `sherlock workspace` |
| Image built from | `build/agent.Dockerfile` | `build/workspace.Dockerfile` |
| Runs as | `nonroot`, uid 65532 | root |
| Shell in the image | none | yes |
| Serves | the HTTP gateway | the gRPC data plane (Read, Write, List, Exec) |
| Repository example | `configs/agent.yaml` | `configs/workspace.yaml` |

**The *Runs as* row is what the image sets, not what the pod asserts.** Each cell is that container's Dockerfile `USER`, and an orchestrator admitting the pod reads neither Dockerfile. What a manifest has to assert about these two, and which Pod Security Standard the pair can reach, is §Capabilities.

**Neither base image is named here.** Each is pinned by digest in the Dockerfile the *Image built from* row names, and that is the only copy (§Images and tags). A row that restated the versions went stale the last time a base moved, and was read as current because its other cell still was (#591); what an operator plans around is the consequence below rather than the version.

Two consequences an operator plans around:

- **The agent image carries no shell and no interpreter.** It carries the platform binary and the operator-installed tool executables it spawns (ADR 0017, ADR 0021); the executables are statically linked Go binaries, the manifests are JSON, and nothing in `/opt/sherlock/tools/` is a shell or an interpreter. `kubectl exec` into that container gets nothing; its diagnosis is logs and the gateway. The workspace image carries the shell its Exec path runs.
- **The workspace container needs root**, because it drops Exec children to another uid. The agent container never needs it.

## Listeners and the bind gate

| Listener | Default | Setting | Environment |
|---|---|---|---|
| Gateway HTTP | `127.0.0.1:8080` | `addr` | `SHERLOCK_ADDR` |
| Workspace gRPC | `127.0.0.1:8081` | `addr` | `SHERLOCK_ADDR` |

The agent finds the workspace through its own `workspace-addr` (default `127.0.0.1:8081`) and publishes it to every tool it spawns as `SHERLOCK_WORKSPACE_ADDR`. The agent never dials the workspace itself; the tools do (`environment.md`).

**The bind gate, as a deployment fact** (ADR 0012). Both listeners refuse to serve beyond localhost unless something authenticates the caller:

- **Gateway, no `tls:` section, non-loopback `addr`** — refuses at startup. The pod crash-loops. This is what a pod spec that sets `addr: 0.0.0.0:8080` to be reachable from a Service hits first.
- **Gateway, no `tls:` section, loopback `addr`** — starts, and a Service in front of it reaches nothing. Nothing in the pod's status says so; the startup log carries `auth="none: loopback binds only"` at INFO.
- **Workspace, non-loopback `addr`** — refuses at startup, with no TLS escape hatch: its gRPC listener is unauthenticated until contract authentication exists. **The workspace can never be fronted by a Service.** It is a same-pod sidecar reached over localhost, which is what makes the shared network namespace part of the deployment rather than a convenience.

Serving the gateway beyond localhost means setting the `tls:` section — `cert`, `key` and `client-ca`, all three or none.

**Replacing that material is a restart, and the restart drops the accepted queue.** All three files are read once, while the process starts (`internal/config/tls.go`); nothing re-reads them and no signal reloads them, so new files take effect only when the process starts again. That restart discards every message the gateway accepted and has not yet taken into a turn (§Shutdown and the grace period), so replacing a certificate is not transparent to senders.

## Volumes and ownership

| What | Setting | Default | Written by |
|---|---|---|---|
| Memory store | `memory-path` | `data/memory.db` | agent container |
| Outbox | derived, not separately settable | `outbox/` beside `memory-path` | the `message_send` tool, which the agent container spawns |
| Workspace directory | `workspace` | `data/workspace` | workspace container |
| Tools tree | `tools-dir` | `./tools` (resolved to `/opt/sherlock/tools` in the sherlock-agent image by `SHERLOCK_TOOLS_DIR`, ADR 0021) | baked into the sherlock-agent image at build time; overridable at runtime by mounting `/opt/sherlock/tools` |
| Ego file | `--ego-file` (flag only) | none: the ego embedded in the binary | the operator |
| Operator instructions file | `--instructions-file` (flag only) | none: the instructions carry no operator part | the operator |

- **One agent process on a host writes a memory store.** Before opening `memory.db` the agent takes an exclusive `flock` on `<memory-path>.lock`, named after the store's resolved real path, and holds it until the store closes after shutdown's drain, or until the process exits (ADR 0002). A second agent, or a one-shot `sherlock agent --message` run, against the same store fails at startup (§Startup). The lock file stays beside the store after exit, and its presence refuses nothing. **The lock is single-host only.** It is not remote fencing: two pods on different nodes that mount the same volume, or a copy of it, are not refused by it, and keeping one writer across hosts is the lifecycle authority's job, not Sherlock's.
- The workspace directory is created on first use. When the workspace runs privileged it chowns that directory to `exec-uid` and gives every file it writes over the contract to the same uid, so contract writes and Exec children share one owner (ADR 0008). An unprivileged workspace owns the directory itself.
- The tools tree is read at startup only — one `manifest.json` per `tools/<name>/` directory, plus the executable the manifest names. It can be mounted read-only.
- The ego and operator instructions files are each read once at startup, so a change applies on restart, and either can be mounted read-only. Neither is mode-checked. The agent places the operator instructions between the ego and the platform contract and interprets nothing in them; naming an instructions file never replaces the ego (`agent.md`, ADR 0024).
- **The source archive grows with completed turns.** Visible user and assistant messages are archived in `memory.db`; each full four-message batch creates one mid episode, stored with its summary's embedding and linked directly to those sources. Short memory is the rolling recent conversation (`memory.md`, ADR 0006). This design has no archive eviction; plan volume capacity from the observed turn rate. The bounded rolling context and recall result count limit prompt size, not database size.

**Two writable volumes, not one shared filesystem.** The agent container writes the memory store and the outbox beside it; the workspace container writes the workspace directory; and nothing the two containers exchange goes through a file. The tools that need the workspace dial its gRPC data plane instead — `file_read`, `file_write`, and `file_list` over Read/Write/List and `shell_exec` over Exec (`environment.md`, ADR 0017) — and no agent-side path resolves under the workspace directory, `workspace` being a setting only `sherlock workspace` reads (`internal/config/`). So the two sets may sit on separate volumes, and neither container needs a filesystem the other holds at the same time. The fourth row above adds no third volume of state: the tools tree is the operator's install rather than anything the agent writes. The sample deployment mounts one root into both, which is that file's convenience rather than a requirement (`deploy/local/docker-compose.yml`).

**What the workload requires of them is survival, not sharing: an agent's volumes must outlive a reschedule.** That is a durability property and not a capacity one, and it is the failure that looks like success — the pod runs, the data persists, and the loss happens when the pod moves. Which storage satisfies it is the orchestrator's. No storage class, default, or access mode is named here: this repository cannot read a cluster, so a claim about one would go stale with nobody in a position to notice.

**The outbox is on the agent's volume, and that decides where a consumer of replies can sit.** It is derived from `memory-path` rather than separately settable, so it lands wherever the memory store does. A consumer that reads it has to reach that volume — another container in this pod, or the agent container itself, whose one-shot `sherlock agent --message` run echoes what the turn delivered. A consumer that watches the gateway's monitoring stream instead needs no volume at all, and the agent's stays private to the agent container; the two are not the same record, though, because that stream is lossy and carries a turn's outcome, where the outbox holds the addressed replies and is durable once each entry's name appears (`gateway.md`). Entries survive a restart on that volume, and Sherlock never removes one: clearing a forwarded entry is the consumer's, after its destination acknowledges it (ADR 0007). Which of them a deployment collects from is therefore a storage decision before it is a delivery one.

**Owner-only files.** Three files are mode-checked, and one of them is the workspace's: the agent's config file, the agent's `tls:` server key, and the workspace's config file. The check lives in the loader both processes share (`internal/config/`), so `workspace.yaml` carries the same rule as `agent.yaml`. `0600` and `0400` pass; `0644` fails and the process exits. Kubernetes projects Secret and ConfigMap volumes at `0644` by default, so **all three** need an explicit `defaultMode` — a sidecar whose config is mounted at the default crash-loops exactly as the agent would. The certificate and the client CA are not checked.

## Configuration and secrets

Settings resolve in one precedence: **flags > `SHERLOCK_*` environment > config file > defaults.** The environment name is the setting with dashes and dots replaced by underscores, so `tools-dir` is `SHERLOCK_TOOLS_DIR` and `model.base-url` is `SHERLOCK_MODEL_BASE_URL`.

Config files resolve in order: explicit `--config <path>`, then `./configs/agent.yaml` for the agent or `./configs/workspace.yaml` for the workspace, then `os.UserConfigDir()/sherlock/config.yaml` or `os.UserConfigDir()/sherlock/workspace.yaml`, respectively (`internal/config/`). Missing automatic files fall through to defaults; a missing explicit path fails startup. From the repository root, run `chmod 0600 configs/agent.yaml configs/workspace.yaml` before starting either process: Git does not preserve owner-only modes. Relative settings still resolve from the process working directory. The local Compose deployment keeps its separate `deploy/local/agent.yaml`, mounted and selected explicitly as `/etc/sherlock/config.yaml` (`deploy/local/docker-compose.yml`).

**A config-file key no setting reads is reported, not refused.** Both processes warn once per unread key, naming the key and the file, and start anyway — so a renamed key does not reject an operator's whole file. The warning is the only signal, and it reaches a log inside the container and nothing else.

**`--strict-config` refuses what the default reports** (#932). On either command, every key that would be warned about fails startup instead, and the error names the keys and the file; a process that started under it has read every key its file carries. It is a flag only, like `--agent-id`: it is read off the command line rather than through the settings layers, so neither `SHERLOCK_STRICT_CONFIG` nor a `strict-config` key in the file it checks turns it on or off — the file's key is itself an unread key. Without the flag, startup is unchanged.

Exceptions a pod spec meets immediately:

- **Both commands name their listener `addr`**, so a single `SHERLOCK_ADDR` set on the pod retargets both containers. Set it per container, or leave the workspace at its default.
- **`--agent-id` is a required flag with no default.** It is read straight off the command line rather than through the settings layers, so setting `SHERLOCK_AGENT_ID` in the pod spec does not choose the agent's ID, and an absent or empty value fails startup (§Startup). The value is opaque and used verbatim: a GRN is the path segment the routes answer on. The agent then publishes the ID it resolved under that same name for the tools it spawns, so a value already in the environment is replaced rather than read — `message_send` reads it there to stamp each delivered message (ADR 0016).
- **`--assignment-epoch` is an optional flag with no environment form.** It is the launcher's label for this assignment: opaque, empty meaning unknown, logged on the `agent listening` line, and published to the tools as `SHERLOCK_ASSIGNMENT_EPOCH`, replacing any value already in the environment — `message_send` records it on each outbox entry.
- **The generation is a runtime start nonce, not a setting.** Each serving start mints a fresh 32-character lowercase hex value after the memory store's writer lock is held, logs it on the `agent listening` line, publishes it to the tools as `SHERLOCK_GENERATION` (empty in a one-shot run, which mints none), and persists it nowhere, so a container restart under the same args carries a new one. There is no `--generation` flag; passing one fails startup as an unknown flag. Sherlock checks neither value (ADR 0016).
- **`--ego-file` and `--instructions-file` are flags with no environment or config-file form.** Each is read straight off the command line, so neither `SHERLOCK_EGO_FILE` nor `SHERLOCK_INSTRUCTIONS_FILE` names a file, and a key of either name in the config file is an unread key. Empty or absent selects the embedded ego and no operator instructions respectively.
- **`revision` is the configuration's name, not a setting the agent acts on.** It is a top-level config-file key, opaque, set by whatever writes the desired configuration and covering the ego and operator instructions as well; the agent echoes it as `config_revision` on its status route and computes nothing from it. Absent or empty means unknown. Like every key it resolves through the precedence above, so `SHERLOCK_REVISION` overrides the file's value.
- **`tools.pins` has no environment form, and `SHERLOCK_TOOLS_PINS` fails startup rather than being ignored.** It is a nested map — one variable carries one value — reachable through the config file only. Setting the variable is refused while the config resolves, empty value included, and the refusal names the file to write the pin set in (#745). A per-tool variant such as `SHERLOCK_TOOLS_PINS_FILES` names no key and is ignored.

**The model API key never appears in configuration** (ADR 0003). `model.api-key-env` names the *environment variable* that holds it, defaulting to `OPENAI_API_KEY`; `embedding.api-key-env` does the same for the embeddings endpoint and defaults to empty, which sends no key. The key reaches the process through the environment and nowhere else, so it is injected as a Secret-backed environment variable rather than a mounted file.

**Every tool the agent spawns inherits the agent's whole environment**, the model key included — the runner starts the child from `os.Environ()` rather than from empty (`internal/tool/`). This is the decided posture, not a defect: security is drawn by environment and a tool is inside the agent's one (#543, `security.md` §Tool trust posture). An operator choosing what to put in the agent container's environment is choosing what every installed tool can read, so a credential meant for one tool is readable by all of them, and **installing a tool is a trust decision rather than a capability one**. **There is no per-tool credential scope, and no manifest field to reach for**: the manifest carried an `env` field that did nothing, and #550 removed it rather than document it (ADR 0009). A deployment that needs one tool to hold a credential the others cannot read needs a second agent, with its own environment and its own tool set.

**What the operator must put in the agent's environment for the shipped tools.** The platform sets `SHERLOCK_WORKSPACE_ADDR`, `SHERLOCK_OUTBOX_DIR`, `SHERLOCK_AGENT_ID`, `SHERLOCK_ASSIGNMENT_EPOCH`, `SHERLOCK_GENERATION` and, per tool call, `SHERLOCK_IN_REPLY_TO` itself, so a deployment supplies none of them. What is left is `tools/github`, which reads `GH_TOKEN` and will not run without it, and optionally `GITHUB_API_BASE` to retarget an enterprise host. Both are the operator's to set, and both are readable by every other installed tool once set. This list is held against the tools' own reads by a test in `internal/tool/`, so a shipped tool that starts reading a new variable fails the build rather than starting up without a value.

The workspace's Exec children are unaffected: they get a scrubbed environment (ADR 0003).

**Sources commit before synthesis.** Completed turns archive visible user and assistant messages before a model call synthesizes each full four-message batch into a bounded mid episode, which is then embedded. A synthesis or embedding failure preserves the sources and episodes for retry at the next completion or startup; startup catch-up can itself fail if either fails, and on a file from before embeddings it embeds every stored episode first. On a file from before entities, each completed turn is followed by one more synthesis call that names the entities of one older episode, until every episode is linked; a failure there is logged and does not fail the turn. Compaction trims the rolling short context without deleting archived messages, and a restart restores recent visible conversation. Populated addressed and extractive conversation stores are refused without mutation: preserve the database and its WAL for inspection with the previous binary, and choose a fresh `memory-path` for episodic memory (`memory.md` §Existing databases, ADR 0002).

**Recall adds one embedding call before the reasoning loop and no model call.** The task text is embedded on the turn's critical path, so an unreachable embeddings endpoint fails the turn. Context combines the two most recent mid episodes with up to five more, taken in turn from those most similar to the task and those an entity walk reaches from the names it contains, and up to four pending source previews. The recall event reports whether any of these entries were added, not whether they answer the question. Exact detail requires a subsequent reserved inspection call for an original source message during the act loop (`memory.md`, ADR 0019).

**Every outbound destination is the operator's choice and none is the model's** (ADR 0013): replies through `message_send`, capabilities through the operator-installed tools, and the reasoning loop's and memory's model and embedding traffic through the operator-configured base URLs. A NetworkPolicy for this pod is written from the operator's own configuration, not from a list this repository holds.

**Outbound delivery is a directory, not a network hop.** `message_send` writes one entry per message, `<id>.json`, into the outbox directory the gateway names for it, and Sherlock forwards nothing onward (`gateway.md`, ADR 0007). Whatever consumes the agent's replies reads that directory, so it is a volume the deployment has to mount and collect from — not a destination it configures. The consumer reads only `*.json` names, since the write's temporary file is dot-prefixed and has no `.json` suffix. The write renames without replacing (`renameat2` with `RENAME_NOREPLACE`), so the volume's filesystem must support it; one that does not fails the tool call rather than risking an overwrite. A consumer bounding its retries by age reads the entry's `created_at` — RFC 3339 in UTC, taken from the agent container's wall clock, so the host's clock is what it measures against — and never the file's mtime or its name: the ID is opaque. An entry without `created_at` was written before the field existed and has no known age (ADR 0007).

## Capabilities

The workspace container needs five, and they divide on a line that decides the pod's Pod Security Standard:

| Capability | For | PSS `baseline` |
|---|---|---|
| `SETUID`, `SETGID` | dropping the Exec child to `exec-uid` | allowed |
| `CHOWN` | handing the workspace directory to `exec-uid` | allowed |
| `KILL` | signalling that child on expiry — the drop leaves it owning neither of the workspace's uids | allowed |
| `SYS_ADMIN` | `unshare(CLONE_NEWNET)` — the fresh, empty network namespace an Exec child gets per call | **not allowed** |

**Target `baseline`, and do not target `restricted`.** `restricted` is reached only where every container in the pod runs non-root, and one here does not: the workspace drops Exec children to another uid, which is where ADR 0010 puts the execution boundary, so it runs as root (§The two processes). Admission evaluates the pod and the two containers share one (ADR 0017), so what the agent container could satisfy alone decides nothing — on its own it would pass `restricted`, which is what makes this workload read as one manifest away from a standard it cannot reach. Getting there means moving that boundary, which is a change to ADR 0010 rather than to a manifest, and nothing has proposed one. `baseline` is what is left, and the `SYS_ADMIN` row is what reaching it costs.

**A manifest asserts the agent container's non-root run; the image's `USER` does not.** Set `runAsNonRoot: true` on that container's security context. The *Runs as* row in §The two processes is the image — `build/agent.Dockerfile` declares `USER nonroot` — and an orchestrator enforcing non-root reads what the pod asserts rather than what the image ships, so a manifest that leaves the question to the image is refused at admission with nothing in the image and nothing in this repository having been wrong. A numeric `runAsUser` is not the assertion either: it states which uid to run as and asserts nothing about that uid, so a value that is not zero reads as non-root to a person and to nothing else.

**`SYS_ADMIN` is netns creation, and it cannot be moved to an initContainer.** The unshare happens inside each Exec child immediately before the credential drop, not once at startup (`internal/workspace/shell/`), so the workspace container holds the capability for its whole life.

**Dropping it does not fail the pod.** Without `SYS_ADMIN` the workspace starts normally and every network-isolated Exec call fails closed with `agent_uid unavailable`. The only signal is a WARN at startup — `CAP_SYS_ADMIN missing; netns-isolated children will report agent_uid unavailable`. Nothing in the pod's status reports it, so an operator who drops the capability to reach `baseline` gets a running agent that cannot execute anything. That is the fail-closed posture ADR 0008 and ADR 0010 choose deliberately: a capability that is unavailable is better than one silently upgraded.

**`KILL` is the deadline, and it is the one that looks removable.** It grants nothing over the node: the container holds its own PID namespace, so the only processes it can reach are the workspace and the children it started. What it buys is the ability to signal them at all. `kill(2)` permits a signal only when the sender's real or effective uid matches the target's real or saved-set uid, or the sender holds `CAP_KILL`, and the drop leaves the child owning neither of the workspace's uids — being root is no substitute once the capability has left the bounding set. Until #612 the shipped set omitted it, and the consequence was invisible: the SIGKILL on expiry did nothing, `Wait` ran until the command finished on its own, and a 100ms deadline took as long as the command did. Single-account mode never needed it, which is part of why it went unnoticed — there the child owns the workspace's own uid.

**Dropping `KILL` now fails every Exec, by choice.** A privileged workspace that cannot signal its child refuses the call with `agent_uid unavailable` and a message naming the capability, rather than running a command whose deadline would pass unenforced. It warns at startup too — `CAP_KILL missing; every Exec will report agent_uid unavailable`. The alternative was to keep serving with an unenforceable bound, which is the shape the defect had.

**The five above are the privileged path's, and a second isolation path needs a host rather than a capability.** `internal/workspace/shell/process_linux.go` carries both: where the workspace is root the Exec child unshares `CLONE_NEWNET` while `CAP_SYS_ADMIN` is still held, and where it is not the child clones `CLONE_NEWUSER | CLONE_NEWNET` with the uid mapped to itself (ADR 0010). The second is what makes "drop `SYS_ADMIN`, run unprivileged, keep the isolation" look available. It is not a shape this document supports — the workspace container needs root (§The two processes), and the path exists only in the single-account one, an unprivileged workspace whose `exec-uid` is its own uid, any other value failing closed before the namespace is reached. What follows states what that path would require, not that it is offered.

**It requires a host that permits unprivileged user namespaces.** Creatability without privilege is a property of the syscall and not of every host, so it is checked rather than assumed — checked where the workspace would run, as the account it would run as, under the security context it would run under:

- **`user.max_user_namespaces` reads non-zero.** The sysctl is itself namespaced, so a value read on the node answers for the node and not for the pod.
- **`unshare --user --net true` succeeds** with no capabilities added. The sysctl is necessary and not sufficient: it answers for the kernel, while a runtime's seccomp or LSM policy can refuse a clone the kernel would permit, so what settles the question is making the call rather than reading a value.
- **The shell package's single-account netns cases run rather than skip.** They make the call the workspace makes, and the helper they run through turns the fail-closed sentinel into a skip (`internal/workspace/shell/netns_linux_test.go`), so on a host that refuses the clone they skip and `make ci` still passes. A green pipeline is not evidence about this path; those cases running is.

**Unmet, it fails closed as a missing `SYS_ADMIN` does, with one difference.** The clone's `EPERM` becomes the same `agent_uid unavailable` every undeliverable boundary reports, so the call is refused rather than served with the host's network (ADR 0010). The difference is the signal: the `SYS_ADMIN` probe warns at startup only where the workspace is root, so in the single-account shape nothing is probed at startup and the first network-isolated Exec is the first thing to say so.

## Startup: what kills the pod and what degrades it

The list below is the set an operator can trigger from a pod spec, grouped by cause. It is a selection, not the whole of it: the code carries roughly forty distinct startup error sites, and the ones left out are those no deployment choice reaches — a failed `setenv`, an unresolvable executable path, errors reachable only on a non-Linux build. If a pod fails at boot with a message not below, it is one of those.

Every fatal path exits **1** and prints `Error: <message>`; nothing distinguishes them by exit code, so the message is the only diagnosis.

**Relative paths the agent resolves are relative to its working directory; an absolute one is its own.** `build/agent.Dockerfile` declares `WORKDIR /home/nonroot` and sets `SHERLOCK_TOOLS_DIR=/opt/sherlock/tools`, so a relative `tools-dir` like the default `./tools` and `memory-path`'s default `data/memory.db` land under `/home/nonroot/` while the tools tree resolves to the absolute `/opt/sherlock/tools` (ADR 0021). A pod that sets `workingDir` moves every relative path at once and an absolute one is what the env or config says.

**Kills the process at startup:**

| Cause | Process | Message shape |
|---|---|---|
| `--agent-id` absent or empty | agent | `--agent-id is required: the agent serves the identity it was given and has no default (ADR 0016)` |
| `--ego-file` names a missing or unreadable file | agent | `ego file: open …: no such file or directory` |
| `--instructions-file` names a missing or unreadable file | agent | `instructions file: open …: no such file or directory` |
| Config file group- or other-readable | both | `config file "…" is group- or other-accessible (mode 0644); it must be owner-only` |
| `--config` names a missing or malformed file | both | viper's parse error |
| `tls:` section incomplete (some of cert/key/client-ca) | agent | `tls: section is incomplete: missing key, client-ca` |
| `tls:` server key group- or other-readable | agent | `tls: server key "…" is group- or other-accessible (mode 0644)` |
| Certificate/key unparseable or mismatched; client CA unreadable or holding no PEM | agent | `tls: load server certificate: …` / `tls: client CA "…" holds no PEM certificates` |
| Non-loopback `addr` without a `tls:` section | agent | `addr "0.0.0.0:8080" is not a loopback bind: serving beyond localhost requires the tls: config section (ADR 0012)` |
| Non-loopback `addr` | workspace | `addr "0.0.0.0:8081" is not a loopback bind: the gRPC listener is unauthenticated and serves loopback only` |
| `provider: openai-compatible` with the named key variable unset or empty | agent | `model.provider "openai-compatible": environment variable OPENAI_API_KEY is not set or is empty` |
| A `model.provider` other than `mock` without `embedding.base-url` or `embedding.model` | agent | `embedding (required with model.provider "openai-compatible"): openai embeddings: base URL and model name are required` |
| `embedding.api-key-env` names a variable that is unset or empty | agent | `embedding: environment variable … is not set or is empty` |
| Stored mid episodes lack embeddings and the embeddings endpoint fails | agent | `embed conversation: …` |
| Unknown `model.provider` value | agent | `unknown model.provider "…" (want "mock", or "openai-compatible" for any endpoint speaking the OpenAI chat-completions wire protocol)` |
| `provider: openai`, the value retired by #613 | agent | `model.provider "openai" names a vendor where it selects a wire protocol: set it to "openai-compatible", which is the same protocol and the same wiring` |
| Tools directory missing or unreadable | agent | `tool registry: tools directory "./tools" does not exist (resolved to /home/nonroot/tools)` |
| A manifest is unreadable, is not JSON, carries an unknown field, or omits `name`/`command` | agent | `load tools/foo/manifest.json: parse manifest: …` |
| A manifest carries the removed `env` field (#550) | agent | `load tools/foo/manifest.json: parse manifest: json: unknown field "env"` |
| Two manifests declaring the same name | agent | `duplicate tool name "files"` |
| A pin set is configured and a tool on disk is not named in it | agent | `unpinned tool "…": not named by the pin set; pin it as <sha256> or remove the tool` |
| A pin set is configured and a manifest's hash drifted | agent | `descriptor drift for "…": pinned=<sha256> fetched=<sha256>` |
| `tools.pins` present and naming no tool | agent | `config: tools.pins is present and names no tool; a pin set is the tools the operator accepted, so an empty one accepts nothing and no agent can start under it` |
| `SHERLOCK_TOOLS_PINS` set, with any value | agent | `config: SHERLOCK_TOOLS_PINS is set, and the environment cannot express tools.pins: a pin set maps each tool name to its manifest SHA-256, and one variable carries one value` |
| `message_send` is absent from the tools tree | agent | `tool registry: required tools missing: [message_send]` |
| `memory-path`'s directory cannot be created, or the store cannot be opened | agent | `mkdir …: read-only file system` / `open "…": …` |
| Another process on this host holds the store's writer lock — a running agent, or a one-shot run, on the same `memory-path` | agent | `"…/memory.db.lock": another process owns the memory store` |
| `--require-store` set and `memory.db` absent, empty, or holding no Sherlock schema | agent | `"…/memory.db" is absent: memory store is not initialized: --require-store refuses to start without an initialized memory store; a first start that creates it runs without the flag` |
| Workspace directory cannot be created, chowned or chmodded | workspace | `create workspace root "…": …` / `chown "…" to uid 1001: …` |
| Listen address already bound or rejected | both | `listen tcp …: bind: address already in use` |

**Starts, and degrades:**

| Cause | Effect |
|---|---|
| No `tools.pins` section | Drift pinning is off; the tree loads unreviewed. WARN: `tool drift pinning disabled: no pin set configured` |
| No `tls:` section on a loopback bind | The gateway serves unauthenticated on localhost. INFO field only: `auth="none: loopback binds only"` |
| `SYS_ADMIN` absent | Network-isolated Exec fails closed. WARN at startup, nothing afterwards |
| The host refuses the unprivileged user namespace, and the workspace runs unprivileged | Network-isolated Exec fails closed with `agent_uid unavailable`. No startup check, no warning (§Capabilities) |
| `KILL` absent, and `exec-uid` is not the workspace's own uid | **Every Exec fails closed** with `agent_uid unavailable: CAP_KILL is absent, …`. WARN at startup |
| `exec-uid` unreachable — the workspace runs unprivileged and `exec-uid` is not its own uid | **Every Exec fails closed** with `agent_uid unavailable`. No startup check, no warning |
| `exec-timeout: 0` | Every Exec without a per-call timeout fails: `shell: timeout is required`. No startup check |
| Embeddings endpoint wrong or unreachable | Startup calls it only for stored episodes still lacking an embedding. Once an embedded episode exists, every turn fails at recall with `embed conversation: …`; a new episode is kept and embedded at the next completion or startup |
| `workspace-addr` wrong or unreachable | Nothing dials it at startup; tools fail when first called |
| A tool's `command` names a missing executable | Startup is clean; the call fails |
| A directory in the tools tree without a `manifest.json` | Skipped silently, with no log line |

Three traps in that second table are worth naming separately, because they produce a healthy-looking pod that cannot work: **an unreachable `exec-uid`**, **a missing `SYS_ADMIN`**, and **a host that refuses the unprivileged user namespace**. Each leaves exec dead — the third only for the calls that ask for isolation — with nothing in pod status to show it. Run the workspace privileged, or set `exec-uid` exactly equal to the container's `runAsUser`; the second of those is the single-account shape, where isolated Exec then rests on the host permitting unprivileged user namespaces (§Capabilities). A missing `KILL` used to be another and worse one, because it left exec *working* with its deadline unenforced; it now fails closed like the others.

**Choose `exec-uid` as a uid nothing else on the node runs as.** Containers share the node's uid space and `RLIMIT_NPROC` counts every process of the real uid, so a shared account spends the child's 64-process budget on processes that are not the child's. The code default is `1001`, which is the login user on many hosts; the sample deployment overrides it to `10001` for exactly this reason (`deploy/local/docker-compose.yml`).

**A stalled workspace is refused by its caller, and `exec-timeout` still decides how long a command runs.** `exec-timeout` bounds the command the workspace runs, not the RPC carrying it, so a workspace that accepts the connection and then answers nothing — a deadlocked handler, a process stopped mid-call — never reaches it, and the queue serialises runs, so one such call stops every later message for that agent with nothing in the pod's status to show it (§Health and readiness). Each tool therefore sets its own deadline on the data-plane call: each file tool waits what a pod-local filesystem call needs, and `shell_exec` waits the per-call timeout it was handed plus a margin for the workspace's dispatch. **A call naming no timeout is bounded against the stall alone**, because the ceiling is then `exec-timeout`'s and a tool in the agent container cannot read it — so that bound is required to clear the ceilings `exec-timeout` is given, and raising `exec-timeout` needs no matching change here. gRPC carries a caller's deadline into the executor, so a bound taken from a command duration instead would cut short every command a longer `exec-timeout` allows; what keeps this one clear of it is a test rather than a line in this document.

**`tools.pins` absent and `tools.pins: {}` are different, and an empty section does not start.** An absent section leaves pinning off and warns. A present but empty section is rejected while the config resolves, because it is an unfinished configuration rather than a stricter one: "accept no tool" has no running form. `message_send` is required and the required set is not operator-configurable, so a pin set naming nothing refuses the mouth and the agent stops whatever else the tools tree holds. Name each tool and the hash the agent logs for it on the `tool manifest loaded` line, or remove the section to run unpinned.

**Upgrading with `tools.pins: {}` already in a config file will stop the pod from starting, and that pod was not pinned before.** Until #562 an empty section resolved to the same value as an absent one and quietly left pinning off, so a deployment carrying it has been running unpinned while reading as strict. The startup failure is the first accurate signal it has had.

**`--require-store` tells a lost store from a first start, and the launcher says which one a start is.** Without it the agent creates `memory.db` on first use, so a volume that lost its store restarts as a blank agent with no error. With it the agent refuses a store that is absent, empty, or holds no Sherlock schema, after the writer lock is held and before anything migrates or catches up, and creates, repairs and resets nothing — the lock file beside the store is the one file it leaves. The flag is read off the command line alone, never from the config file or a `SHERLOCK_*` variable, so the start that creates the store is an ordinary launch without it. It does not tell this agent's store from another agent's (ADR 0025).

**A one-shot `sherlock agent --message` run skips the TLS and bind gates entirely**, because it never serves. A Job that smoke-tests configuration will not catch a broken `tls:` section or a non-loopback `addr`.

## Health and readiness

**`GET /agents/{agent-id}/status` is the probe route** (ADR 0022). It answers 200 with `{"contract_version":1,"agent_id","assignment_epoch","generation","config_revision","state","started_at"}` and does nothing else: it enqueues no message, reads no store and holds no stream open (`internal/gateway/handler.go`). Like every route it is agent-addressed — a request naming any agent ID other than the process's own returns 404, so the probe path carries that exact value — and where `tls:` is set the probe must present a client certificate (the gateway requires and verifies one). The workspace registers no gRPC health service.

- **Every value is what this process loaded.** The route is served only once startup has succeeded, so a process that answers it has its memory store open under the writer lock and its generation minted; one that cannot serve it reports nothing, and the caller timestamps its own observation. `assignment_epoch` and `generation` are the identity values of §Configuration and secrets, `config_revision` echoes the config file's `revision` key, and an empty one of the three means unknown — the agent does not refuse to start without them.
- **`started_at` is the process start time.** By itself it says nothing about which revision was applied; `config_revision` is the claim about that.
- **`state` is `serving`, or `draining` once `SIGTERM` has arrived** (§Shutdown and the grace period). A readiness probe that should take a draining pod out of rotation reads that field: the route keeps answering 200 through the drain.

**`POST /agents/{agent-id}/messages` is not a probe.** The message goes into the agent's inbox — a bounded channel (`DefaultQueueCapacity`, 64 messages, `internal/gateway/queue.go`) drained by serial turns, each taking a bounded batch (`MaxDrainBatch`, §Load-bearing facts) — and the agent runs a turn on it like any other message. A periodic post therefore competes with the agent's work instead of observing it: it spends turns and model calls, it takes drain slots from real senders, and once the inbox is full the enqueue blocks the caller until a turn frees a slot. `GET /agents/{agent-id}/events` enqueues nothing either, but its response is a stream that ends only when the client disconnects, so it costs a probe a held connection and a timeout of its own.

**`agent listening` is not a readiness signal.** The agent logs it before the listener binds, so a pod that cannot bind logs a successful-looking startup line and then fails. The workspace logs `workspace listening` after its bind, so the two containers' logs do not mean the same thing.

## Shutdown and the grace period

Both serving processes trap `SIGTERM` and `SIGINT`. A one-shot `sherlock agent --message` run installs no signal handler at all — it runs to completion or dies.

- **Agent** — drains, in this order (ADR 0022, `internal/gateway/httpserver.go`):
  1. `state` turns `draining`;
  2. a new `POST /agents/{agent-id}/messages` answers 503 `{"error":"draining"}`, and the listener stays open;
  3. the turn in flight runs to completion, durable writes included — sources, note, episodes and outbox — rather than being cancelled;
  4. no queued turn starts, the after-turn pass that names a stored episode's entities is skipped (it is idempotent, so the pass after the next completed turn picks up what it left), and the monitoring stream ends;
  5. the listener closes, draining in-flight HTTP requests **bounded at 10s**, then memory closes and, last, the store's writer lock is released;
  6. the process exits.

  The wait in step 3 is unbounded. The close issues no network request, because the store has no provider to call (ADR 0018).
- **Workspace** — `GracefulStop`, which waits for in-flight RPCs with **no bound**. In practice an in-flight Exec is bounded by `exec-timeout` (default 30s). Exec children carry `Pdeathsig`, so they die with the workspace process.

**A draining agent declines the request; it does not refuse the connection.** Until the turn in flight has finished, a sender posting gets 503 `draining` and can redeliver the same message ID to the next process (`gateway.md`); a lookup and the status route keep answering. Only after the drain does the listener close, so a sender arriving then gets TCP connection refused — not distinguishable from a pod that crashed, and the status route is gone with it.

**A restart discards the queued messages.** The drain finishes the turn in flight and starts no other, and the queue is held in memory with nothing writing it down (`internal/gateway/queue.go`, `gateway.md`), so every message accepted but not yet taken into a turn stays uncommitted and is lost. The sender holds its 202 and is told nothing more, because a message no turn took reaches no monitoring event — so a consumer treating the 202 as an end-to-end acknowledgement is counting messages the agent never read. A consumer that looks the message up after the restart finds it unknown and can redeliver it under the same ID (`gateway.md`). Every way the process ends costs this: a rolling update, an eviction, a crash, and the `SIGKILL` at the end of the grace period alike. An operator who needs the buffer empty stops posting and lets the agent work it off before the pod is stopped.

**No total shutdown deadline exists** — not as a flag, an environment variable, or a config key. The orchestrator's grace period is the only total bound: the turn in flight runs for as long as it takes, and the 10s HTTP drain comes after it. A turn the `SIGKILL` cuts off commits nothing, so its messages read unknown after the restart and the sender redelivers them — delivery is at least once, never exactly once. Derive `terminationGracePeriodSeconds` from the longest turn you expect — your own `exec-timeout`, provider timeouts and tool budget — rather than copying a number from here, and expect this document to state one when the code does.

## Snapshot and restore

The supported boundary for copying one agent's stored state and starting an agent on the copy (#937). The procedure is `deploy/runtime-fixture/snapshot.sh` (`copy`, `verify`, `restore`), and the runtime fixture runs it on every pass (`tests/runtime_fixture_test.go`). Nothing in Sherlock takes a snapshot on its own; this is what an operator or a lifecycle authority may rely on when it does.

- **What the stored state is.** Everything on the agent's volume (§Volumes and ownership): `memory.db` with its `-wal` and `-shm` — sources, the note, episodes, entity links and the completion records — and `outbox/` beside it. The writer lock `<memory.db real path>.lock` is not state, and the workspace directory is not part of it.
- **A consistent copy is taken only from a drained, positively stopped writer.** Positively stopped means two things: the process has exited after its drain (exit status 0, §Shutdown and the grace period), and its writer lock is free. `copy` takes that lock itself and holds it for the whole copy, so it refuses a store whose lock is held, and a writer starting on this host mid-copy fails at startup instead.
- **The files go together, and an absent one stays absent.** `memory.db`, `-wal` and `-shm` are copied together with `outbox/`. A cleanly closed store usually has neither sidecar, so one that is absent is recorded as absent and never created. Each file's hash goes into a manifest, and the copy is read back against its source before `copy` reports success.
- **A copy is verified by opening it.** `verify` checks the hashes again, then opens a scratch duplicate, because opening a store can checkpoint its WAL and the snapshot has to stay the bytes that were copied. It runs SQLite's integrity check and reports the source count, the completion records, the episodes and the note as identifiers and hashes, and each outbox entry's ID, `created_at`, origin fields and content hash. It reports no memory content.
- **A restore goes to a fresh path and replaces nothing.** Pending outbox entries come back byte for byte, `created_at` and the origin fields (`agent_id`, `assignment_epoch`, `generation`) included. The agent started on the copy mints a new generation, so an entry names the start that wrote it, not the one now holding it. A consumer that already collected an entry from the original finds it again in the restored outbox, so it deduplicates by entry ID. Completion records come back too: a message completed before the snapshot reads `completed` on the restored agent, and one completed after it reads `unknown`, which tells its sender to redeliver.
- **Activation is blocked while it cannot be established that the old writer stopped.** That covers a held lock, an exit nobody observed, and every writer on another host, which the lock cannot see (§Volumes and ownership). Sherlock states the condition and does not enforce it. Not starting a restored copy while the old writer might still run is the lifecycle authority's job.
- **No live move and no deletion.** The procedure copies. It never moves or deletes the source, and nothing here migrates or removes existing memory.

Two startup refusals sit next to this one and neither is it (ADR 0009 invariants 2 and 5). The other depends on no configuration at all: the registry refuses to start without `message_send`. Neither reaches further than the manifests — not the executables beside them, and not which revision the agent image reading them was built from.

## Load-bearing facts

Everything else in this document is **descriptive**: true, useful, and free to change. The facts below are **load-bearing** — the `sherlock-operator` team's correctness depends on them, so changing one is a contract change and they are the party to tell. This list is exactly the set they named; a fact nobody has said they depend on stays descriptive until someone says otherwise.

| Fact | Value today | Where | What breaks on their side |
|---|---|---|---|
| The bind gate | no `tls:` ⇒ loopback binds only, enforced at startup | `internal/config/loopback.go` | Their CRD decides Service and TLS wiring from it. Relaxing it changes what a pod without `tls:` exposes; tightening it crash-loops pods their CRD used to accept |
| Owner-only file mode | `0600`/`0400` pass, `0644` fails | `internal/config/owner_only.go` | Their generated Secret volumes set `defaultMode` because of it. Widening it silently loosens their posture; extending the check to more files fails deployments that were valid |
| `exec-uid` must be a dedicated account | default `1001`; `RLIMIT_NPROC` (64) counts every process of the real uid, and joins only in the privileged drop | `internal/workspace/shell/` | They allocate a uid nothing else on the node uses. If the cap stopped being per-uid, their allocation is unnecessary; if a shared uid became acceptable, their constraint is wrong |
| `MaxDrainBatch` | `8` | `internal/gateway/runner.go` | How many queued messages one turn takes. Their queue-depth alerting and backlog expectations are derived from it |
| `SubscriberBuffer` | `32` | `internal/gateway/events.go` | A monitoring subscriber loses events past this many undelivered, with nothing in the stream marking the gap (`gateway.md`). Their consumer's reconnect and gap handling assume this number |

## Open questions

- **What moves a base-image digest when the tag does not.** A digest receives no security patch; a tag does, and pinning gave that up deliberately. `.github/dependabot.yml` raises a pull request when a base image's tag moves to a new version, which is the covered half. The other half is not covered: Dependabot's docker ecosystem offers version updates and no security-update channel, and a digest refresh under an *unchanged* tag is conditional rather than promised. So a base republished with a CVE fix under the same tag may raise nothing, and the fallback is re-resolving the digest by hand. Determined on 2026-08-17 from GitHub's supported-ecosystems table and `dependabot-core`'s `docker/lib/dependabot/docker/update_checker.rb`; re-check it before relying on the covered half.
- **Whether the dev cluster can pull what a release publishes — closed on both halves, as of the account read on 2026-09-05T20:47+09:00 (four repositories then; two now, after `garam/gagent-{agent,workspace,tools}` were retired on 2026-09-25).** The credential half: `garam-dev-ecr-pull` in this account is assumed by web-identity federation against a self-hosted OIDC issuer — the on-premises equivalent of IRSA — in sessions of at most an hour, so the twelve-hour authorization-token expiry this question rested on is met by that path rather than by someone remembering. The mechanism is `garamsh/infra`'s and not this repository's. **The reach half is answered by an execution rather than by a policy.** That role's inline pull policy names the production two — at the time of that read, `garam/gagent-agent` and `garam/gagent-workspace`, the names this repository held before the rename; under the new path they are `garam/sherlock-agent` and `garam/sherlock-workspace`, and `garamsh/infra` is the only party that can change the role's grant to match — and CloudTrail records fetches through the role against `garam/gagent-agent` (first 2026-09-04T05:29+09:00) and `garam/gagent-tools` (first 2026-09-05T18:43+09:00, against a repository this project no longer publishes; the pull role's grant still named it until that repository was retired). - **Agent-to-sidecar authentication.** The workspace's gRPC listener ships pod-local and unauthenticated, which is what forces the loopback-only rule above (`security.md`, `environment.md`).
- **Whether the gateway should offer a durable accept.** What a restart drops is not open: the queue is held in memory, so a message accepted but not yet drained is lost (§Shutdown and the grace period, `gateway.md`). What is open is whether the 202 should promise more than "queued in this process", and what an accept that survives a restart would cost (#492).
