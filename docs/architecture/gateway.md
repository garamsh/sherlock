# Gateway

Governs the gateway: message ingress, outbound delivery, and monitoring. Rationale: ADR 0017, ADR 0007, ADR 0012, ADR 0015, ADR 0022, ADR 0026.

## Current decisions

- The gateway is the agent's ears and eyes; it lives in the agent container and serves that one agent (ADR 0017). It has no relationship with the sidecar.
- Routing senders to agent pods is the orchestration layer's concern (ADR 0014); the gateway terminates mTLS and nothing more.
- Three flows, unchanged in shape:
  - **Ingress** — asynchronous and fire-and-forget: accept, enqueue, acknowledge. No synchronous response couples a sender to a turn. A message carries its sender's ID, or one the gateway assigns when the sender gave none (ADR 0007). Ingress itself stores nothing at accept time. A completed turn later commits its visible user and assistant messages in a source transaction before synthesizing full four-message batches into mid episodes. Synthesis failure leaves those sources durable and pending for retry (ADR 0006, ADR 0011).
  - **Outbound** — the mouth: `message_send` lives agent-side as the agent's own speech (ADR 0007: outbound is a tool). Delivery is the tool writing one entry per message, `<id>.json`, into the outbox directory it is given as `SHERLOCK_OUTBOX_DIR`; the gateway names that directory and reads it back, and Sherlock forwards nothing onward. There is no push, so there is nothing to fall back from: an entry is durable once its name appears, and a reader of that directory has everything the agent sent (ADR 0007).
    - **Identified.** `id` is assigned once by the write, unique per entry, and is the file name without `.json`. It is opaque: its present time-ordered prefix is an implementation detail, and a consumer must not parse it.
    - **Timestamped.** `created_at` is the agent host's wall-clock instant the entry was minted at, in UTC, in `time.RFC3339Nano` form (variable-length fraction), read once and the same reading `id` is minted from. An entry without it predates the field and has an unknown creation time; a consumer keeps it pending rather than inferring an age from `id` or the file's mtime. The retry budget and clock-skew policy are the consumer's (ADR 0007).
    - **Attributed by the platform, not the model.** `agent_id`, the provenance labels `assignment_epoch` and `generation` (ADR 0016; empty when unknown), and `in_reply_to` — the IDs of the messages the turn drained — come from the tool's environment rather than from the call, so an aggregated outbox stays attributable and the model never states who it is or what it answers. The runner sets `SHERLOCK_IN_REPLY_TO` on each spawn from the call's context, which the session fills with the turn's drained IDs.
    - **Atomic and immutable.** The tool writes a dot-prefixed temporary file in the directory, fsyncs it, renames it to `<id>.json` without replacing an existing name, and fsyncs the directory. A reader takes only `*.json` names and never sees a partial entry. Sherlock never deletes, rewrites or renames an entry; a rerun of an interrupted turn may add entries (at least once).
    - **Forwarded by the consumer.** The consumer removes an entry only after its destination durably acknowledges it, and any current forwarder may forward an entry an earlier process wrote.
  - **Monitoring** — a read-only event stream; every turn emits exactly one terminal event (`turn_finished` or `turn_failed`). Never part of the message path. A subscription is inert: it enqueues nothing and consumes none of the agent's throughput, so an always-attached or periodically-reopened watcher costs the agent nothing (ADR 0014 §Consequences: subscribers watch turns; they do not control them).
- **Status** — `GET /agents/{agent-id}/status` reports what this process loaded once startup succeeded: contract version 1, the agent ID, the assignment epoch, the generation, the config file's `revision` echoed as `config_revision`, `state` (`serving` or `draining`) and the process start time. It reads no store and enqueues nothing. An empty epoch, generation or revision means unknown, and the gateway neither requires nor compares any of them (ADR 0022).
- **Drain on `SIGTERM`** — the state turns `draining`, a new post answers 503 `{"error":"draining"}` while the listener stays open, the turn in flight runs to completion with its durable writes, no queued turn starts and the after-turn pass is skipped, and then the listener closes and memory closes, releasing the writer lock last (ADR 0022, `deployment.md` §Shutdown and the grace period). The orchestrator's grace period is the only total bound.
- **Signed messages** (ADR 0026). A message may carry a signature from an issuer the operator trusts, and the gateway decides who it is from by that signature rather than by who connected.
  - **The signature travels as the body member `signature`**, a string holding a compact JWS (ES256, `typ` `agent-message+jwt`), beside `id` and `content`. Its claims are garam ADR-0101's (`garamsh/garam@1b1189b`, §What is signed); nothing in the code names garam, which is one issuer among any the operator configures.
  - **Trusted issuers are the config file's `issuers`**, each an exact `iss` and one key-set source, `keys-file` or `keys-url` (`deployment.md` §Configuration and secrets). A set is held for its lifetime — the response's `max-age`, one hour when absent, and one hour for a file — read again when it lapses or when a message names a `kid` it lacks, at most once a minute per issuer, and replaced whole by each successful read. While reads fail the held set stays usable for 24 hours past its lifetime. Only P-256 keys with a `kid`, whose `alg` and `use` are `ES256` and `sig` when stated, are kept; other entries are ignored.
  - **The checks run in ADR-0101's order and stop at the first that fails:** the issuer, read from the unverified payload only to choose a set; the protected header, exactly `alg`, `typ` and `kid`; the signature; `aud` equal to `--agent-id` as one string; `exp` later than now minus 60 seconds and `iat` earlier than now plus 60; `content_sha256` over the UTF-8 octets of `content` as received, before redaction, and `message_id` equal to the body's `id`. A body without `id` fails the last. A verified payload whose `sub` is not a non-empty string is refused as `malformed`.
  - **Verification happens at ingress only.** A message that passes is queued and not checked again, so one that expires while it waits still runs.
  - **Verify when present.** An unsigned message is accepted as before, under its transport principal, unless `require-signature` is on. A message whose signature fails is refused and never downgraded to unsigned, so stripping a signature gains a poster only its transport principal.
  - **Verify when present does not let the agent lag behind a sender that signs; two refusals fix the deployment order.** A release before `0.3.0` decodes the body refusing unknown members and has no `signature` member, so it answers every signed message 400 `invalid message body: …` and takes none as unsigned (`internal/gateway/handler.go:85` at `v0.1.0`, `v0.2.0` and `v0.2.1`; line 78 at the development build `837b80afe272`). A release from `0.3.0` on with no `issuers` refuses a signed message at the first check, 403 `signature rejected: issuer`, and never accepts it unverified (`internal/gateway/signature.go:107` at `v0.3.0` and `v0.4.0`). Moving the agent below `0.3.0` once a sender signs refuses every message that sender posts (`deployment.md` §Volumes and ownership). The order is therefore:
    1. The agent on `0.3.0` or later. On its own this costs an unsigned sender nothing: an unsigned message is accepted under its transport principal, and `require-signature` is off unless set (`Verifier.Origin`, `internal/gateway/signature.go:78` at `v0.3.0`).
    2. `issuers` configured and rolled out: a `keys-file` or a `keys-url` from `0.3.0`, or a `keys-url` with `keys-ca-file` from `0.4.0`, the first release that reads `keys-ca-file` (`git grep keys-ca-file v0.3.0 -- internal/` matches nothing; at `v0.4.0` it matches `internal/config/issuers.go`). For garam, configure its `keys-url` with `keys-ca-file`, which needs no re-render, or a `keys-file` its renderer supplies.
    3. The sender starts signing — for garam, garamsh/garam#1258 — and only after step 2 has rolled out.
    4. Optionally, `require-signature`.
  - **Refusals** carry the problem body `{"error":"<text>"}`: a body that is not the accepted JSON object, or a `signature` that is not a string, is 400 `invalid message body: …`; a missing signature under `require-signature` is 403 `signature required`; a failed check is 403 `signature rejected: <check>`, `<check>` one of `malformed`, `issuer`, `header`, `key`, `signature`, `audience`, `time`, `content`, `message id`; a configured issuer with no usable set — never read, or past its grace — is 503 `issuer keys unavailable`. A rejected signature is logged at WARN with its check, `iss` and `kid`, never its content. Verification precedes the redelivery answer, so a redelivery with an expired signature is refused even when its message completed.
  - **The sender is the verified `(iss, sub)`.** It scopes the message ID and is stored with the source (`memory.md`). The turn shows `<sub> (vouched for by <iss>)`, and a message whose `sub` equals its `iss` — the issuer's own notice, such as garam's cross-organization refusal — as `notice from <iss> (no sender to reply to)`; the turn's contract tells the model to reply to the sender and never to a notice's issuer. The request log line keeps `caller_id` as the transport identity and adds `iss` and `sub`.
- One queue per agent; a turn drains the queue (bound 8, sender envelopes, supersede-as-cancellation — ADR 0015). No forced stop, suspend, or steering (ADR 0014).
- **What a sender can and cannot learn about a turn.** This is a contract, not an implementation accident: a 202 that means "accepted" and a 202 that means "received" are different promises, and the difference cannot be seen from outside.
  - The 202 says the message is queued in this process. It does not say a turn ran, or that one will.
  - **A message ID is scoped to its sender** — the issuer and subject a signature verified (ADR 0026), or else the transport principal: the verified mTLS caller identity, empty over plain-HTTP loopback — and kept byte for byte, so a sender redelivers by sending the same ID again (ADR 0007). The two kinds never share a scope. A transport principal names the certificate's subject and never its serial or fingerprint, so it survives a renewal that keeps the subject. Another scope's ID is invisible to a post: posting it delivers a new message of the poster's own.
  - **A lookup answers the transport principal that posted the message**, signed or not, because `GET /agents/{agent-id}/messages/{id}` carries no signature; any other principal reads unknown. Where one poster's ID names more than one message — one unsigned and one signed, or under two issuers — it answers `pending` while any of them is pending, and `completed` once none is and one has committed. A redelivery of a signed message across the switch from unsigned delivery reads as new under its pair's scope and runs once more (ADR 0026 §3).
  - **Redelivery is answered from what the gateway holds.** A message queued or running in this process gets 202 `queued` again and is not queued twice. One whose turn committed its sources to `memory.db` gets 200 `completed` and does not run. Either with other content gets 409. Anything else is a new message.
  - **Completed is the committed sources and nothing weaker.** `GET /agents/{agent-id}/messages/{id}` answers `completed` once the turn's sources, holding that ID and that content, are committed; `pending` while the message is queued or running in this process; `unknown` otherwise. Unknown covers a message this process never saw, one a restart dropped, and one whose turn ended without committing — each is one a sender should redeliver. A restart turns pending into unknown and leaves completed as it was. Content is compared as stored, with credentials redacted (`memory.md`), so two contents differing only inside a redacted credential read as the same.
  - **Delivery is at least once.** Recording is deduplicated, but a redelivered message whose turn never committed runs again, and the effects of the turn that did not commit — a sent message, a tool call — may repeat. There is no exactly-once claim.
  - **The queue does not outlive the process.** It is held in memory and no path writes it down (`internal/gateway/queue.go`), so a message accepted but not yet drained into a turn is lost when the process exits — on a crash and on an orderly shutdown alike, because the drain finishes only the turn in flight. Nothing pushes that to the sender: the 202 has already been returned, and a message no turn ever took reaches no monitoring event. A sender that asks finds the message unknown and can redeliver it. Whether the gateway should offer an accept that survives a restart is open (#492); that the present one does not is a fact about the system today, not part of that question.
  - The monitoring stream is the only channel carrying a turn's outcome — its content or its error — and it is best-effort; the lookup says only whether a message completed. A subscriber that falls behind its buffer loses events while it is still connected, with nothing in the stream marking the gap, and a subscriber that connects after posting sees nothing emitted before it subscribed — the stream has no replay.
  - So an event's presence is information and its absence is not. A missing `turn_failed` does not separate a turn that succeeded from one whose event was dropped or one that never started, and a live connection is not evidence that the stream is complete.
  - A subscriber that is keeping up sees one terminal event per turn, stamped with the message IDs that turn drained (ADR 0015). Those IDs are a hint; the lookup is what says a message completed. A failed turn reaches no other channel: the runner logs it and takes the next batch.
  - An event that does arrive carries the outcome: `turn_finished` the turn's visible content, `turn_failed` the error. An addressed reply to the sender is a separate act by the agent — `message_send` on the outbound flow above.

## Current state

`sherlock agent` runs one agent per process: the agent ID is fixed at startup by the required `--agent-id`, opaque and used verbatim, and each serving start mints its generation — a runtime start nonce — once the store's writer lock is held and before the listener serves (ADR 0016), the HTTP paths keep the `/agents/{agent-id}/` shape, and a request naming any other ID gets 404. `POST /agents/{agent-id}/messages` takes `{"id","content","signature"}` with `id` and `signature` optional and returns 202 with the ID (the sender envelope is the verified signature's issuer and subject, or else the verified mTLS caller identity), 200 for a completed redelivery, 409 for a reused ID, and the refusals of §Current decisions for a signature; `GET /agents/{agent-id}/messages/{id}` reports the status of the messages the caller posted under that ID; `GET /agents/{agent-id}/status` reports the process's identity, config revision and state; and `GET /agents/{agent-id}/events` streams the agent's loop events as SSE. Fan-out is per-subscriber buffered (`SubscriberBuffer`, 32 events) and never blocks the run, so a subscriber that reads too slowly loses events rather than slowing the turn — the stream is lossy by construction, not only under failure. Callers authenticate with mTLS when a `tls:` config section is set; without it the gateway serves loopback only. Outbound delivery is the `message_send` tool writing an entry into `outbox/` next to the configured `memory-path`: the gateway computes that path once (`DirFor`), hands it to the tool in its environment, and reads the directory back to report what a one-shot turn delivered. Delivery has no network hop and no queue behind it, so it neither retries nor reports a failure the tool did not already return. `sherlock agent --message` runs one turn against the same tool list (the operator-installed servers) instead of serving, and exits non-zero if a tool call in that turn failed. The two paths report a failed tool call differently because they have different readers: a served turn hands it to the model, which gets another iteration to react, and the turn still ends `turn_finished`; a one-shot run has exited by the time anyone looks, so its exit status is the only reader left. Neither path branches on a mode or on the configured provider.
