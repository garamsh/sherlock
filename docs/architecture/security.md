# Security

Governs the security model: trust domains, secret custody, and egress. Rationale: ADR 0017, ADR 0009, ADR 0003, ADR 0005, ADR 0010, ADR 0012, ADR 0013, ADR 0014.

## Current decisions

- Two containers, two trust postures (ADR 0017):
  - **Agent container** — holds the secrets (model and channel credentials) and the memory store. Its tool client is the manifest loader and the stdio runner; the agent executes nothing and hosts no tool behavior — the untrusted-code path lives in the workspace.
  - **Sidecar (the workspace)** — serves the gRPC data plane (files and exec) and owns the one untrusted-code path: Exec children drop to the unprivileged exec UID with a minimal environment plus operator grants, rlimits, and operator-controlled network access (ADR 0008, ADR 0010). It enforces the agent's permissions at the action site with Linux users and modes.
- Tools are scripts with manifests under the operator's `tools/` directory (ADR 0017, ADR 0009). The platform owns the manifest format, the stdio call protocol, the boundary validation, and the drift pin. Tools own their description, validation, behavior, and domain security policy (ADR 0005).
- **Tool trust posture.** Security is drawn by environment, and the environments are the two containers. A tool is the agent's own — the tool client is part of the agent's self (ADR 0017) — so a tool the platform spawns runs as a separate process **inside** the agent's environment and inherits it whole. That is not a leak across a boundary; it is what being inside one means. The platform never runs tool code in the agent's address space, and process separation is what that buys — not a narrower set of secrets.
- **So installing a tool gives it every credential the agent holds, the model API key included.** The tool set is a trust decision, not a capability decision: choosing which `tools/<name>/` directories are present (ADR 0009) is choosing who holds the agent's secrets, and nothing at the tool level narrows it. A credential a tool needs belongs in the agent's environment, where every other installed tool can also read it. **A tool cannot hold a credential the agent does not, and no manifest field offers to give it one**: the manifest describes the tool's interface and says nothing about secrets (ADR 0009). It carried an `env` field that did nothing until #550 removed it — removed rather than documented, because a name that promises a per-tool scope is the hazard whether or not the code behind it runs. An operator who needs one tool to hold a credential the others cannot read needs a second agent. **Free contribution, operator installation**: any user may publish a tool, but only the operator chooses which tool directories are present. Self-registration is not a supported shape.
- **Boundary posture on tool inputs and outputs.** The tool's self-description is untrusted input at the boundary. The platform re-validates every fetched descriptor and refuses to load a tool whose schema fails to parse — that one is unconditional. **The drift check is the operator's to switch on**: it compares each manifest's hash against the `tools.pins` set, so an agent configured without one loads whatever is in the tree and says so at startup with a warning naming the hashes to pin (ADR 0009 invariant 2). Where a pin set is configured it is enforced in full and to the manifest's full depth — a nested change to a schema moves the hash, not only a top-level one — and a tool the set does not name is refused alongside one that drifted. **Mounting the tools tree from a digest-pinned image does not stand in for that set**: the digest rules out the tree changing under a reference that did not change, and the pin set rules out a manifest the operator has not accepted loading at all — including one that arrives because the reference itself changed, which is an ordinary configuration edit wherever that reference is held. Where an operator decides to pin, the set is written in the agent's config file and reaches the process through no other layer; that is custody as much as encoding, because the config file is mode-checked owner-only while an environment variable is readable by every tool the agent spawns (`internal/config`). **A non-conforming output fails the call**: the output is dropped, never reaches the model, and the error names the tool; the tool stays installed and the next call runs. Strict schema enforcement at the model API layer (constrained decoding when the provider supports it) prevents the model from emitting arguments the schema rejects.
- Agent model keys, durable memory and configuration stay outside the workspace. Repository credentials explicitly provisioned there are deliberately available to all workspace code (ADR 0003, owner decision #840). The operator grants named workspace environment variables and network access; neither can be granted by model tool arguments. Never mount host home or agent state into the workspace. A process on the host with only a workspace cwd is not a filesystem isolation boundary.
- Workspace code may expose its granted repository credential through output or network. Avoid printing it, enable shell tracing only without secrets, and use a least-authority credential; no output filter or command rewrite is claimed to prevent theft. The token's actual repository/permission scope must be verified separately before claiming it is restricted.

- Each tool's implementation enforces its own domain's policy; no separate security layer exists (ADR 0005). Guard models are defense-in-depth, never a boundary.
- Image hygiene stays a security property: minimal images, no unneeded setuid binaries, dropped capabilities. The image holding the secrets and the memory store carries no shell and no interpreter — the platform binary is the only executable file in it, whatever subcommands that binary links in (ADR 0017). The workspace's image carries the shell its Exec path runs.
- Workspace egress is an operator grant (`exec-network`, default false); once granted, ordinary CLI programs choose destinations subject to deployment network policy. The installed tools and configured model endpoint retain their own agent-side egress. No general broker or proxy mediates either path (ADR 0013).
- **An outbound call a tool makes is bounded by the tool that makes it.** Nothing above one bounds it: the turn carries no deadline into a tool, so a destination that accepts the connection and then answers nothing parks the turn and every message queued behind it (ADR 0015). Nothing below one does either — no operator setting reaches such a call, and the destination's own limit is not one, because the failure this guards against is a destination enforcing none. So the bound is the tool's own to state, it pre-empts no configured ceiling, and each tool states one against what its call is for — for `tools/github`, a single small REST write to the GitHub API. A tool that calls out and states no bound is the defect, not the exception.
- Callers authenticate to the gateway with mTLS (ADR 0012). Caller authorization and capability granting are the orchestration layer's concern (ADR 0014); capability permissions are enforced at the sidecar, the action site.
- Self-destruction is bounded by construction (ADR 0017): executed code can reach only the workspace, which is recreated — never the agent's self.
- A shared sidecar means multi-tenant execution — per-agent accounts on one workspace — and is deferred until the dedicated-sidecar baseline exists.

## Current state

Two processes per agent today. The agent process (`gagent agent`) holds the secrets and the memory store, and its gateway authenticates callers with mTLS when the operator sets the `tls:` section — server certificate, key and client CA, all three or none (ADR 0012). Without that section it serves loopback binds only and a non-loopback bind fails startup, so an unauthenticated gateway is never reachable rather than being reachable and open. Where the section is set, the TLS key and both config files must be owner-only, and the gateway refuses a group/other-readable key or config file at startup. It executes nothing. The sidecar (`gagent workspace`) is the data plane and owns the untrusted-code path: Exec children run through its executor (`internal/workspace/shell`) dropped to the configured exec UID in the workspace directory, with a minimal environment plus explicitly granted workspace variables, mandatory untrusted rlimits, a per-call timeout, and network isolation unless the operator grants the workspace network; a drop the platform cannot perform fails closed with `agent_uid unavailable`, a resource cap it cannot apply fails closed the same way, and so does a deadline it could not enforce — signalling the account it drops to needs `CAP_KILL` (#612) — so no untrusted child runs uncapped or unbounded (ADR 0008, ADR 0010). In single-account mode the workspace marks itself non-dumpable, so a same-account child cannot read its `/proc/<pid>/environ` (ADR 0003). When privileged the workspace chowns the workspace directory to the exec UID, so tool writes and exec'd children share one owner.

The sidecar's gRPC listener is unauthenticated in this phase, so it serves loopback binds only — the same fail-closed posture as the gateway (ADR 0012): an unauthenticated gRPC listener carrying Exec is a remote shell into the workspace, and a non-loopback addr fails startup.

The agent's tool client (`internal/tool`) implements the platform contract: manifest loading, the stdio call protocol, schema validation, and drift pinning where the operator configured a pin set. **One tool is required: `message_send`.** The agent cannot speak without it, so its absence fails startup closed; the required set is hard-coded (`internal/tool`) and there is no operator key that adds to it. The workspace-coupling tools are not in it — removing `tools/file_read/` or `tools/shell_exec/` starts a working agent that has lost those capabilities, which is the operator's choice to make and is the same choice as installing them (ADR 0017). The platform does not mediate permissions at the tool level — the operator is the gate, by directory placement.

## Rejected alternatives

- **Filters or guard models as the boundary** — probabilistic and bypassable by obfuscation; boundaries are structural only.
- **In-body secret substitution (shell wrapper, FUSE, LD_PRELOAD)** — a materialized secret is a stolen secret.
- **Shared sidecar from the start** — multi-tenant execution security before the dedicated baseline exists.
- **A runtime plugin loader for tools (any user self-registers tools at runtime).** Would put arbitrary code next to platform secrets. The contribution shape is "free to publish, operator-installed by directory placement" — that is the only shape that preserves the trust posture while letting any user contribute tools.
- **A permissions policy at the platform level.** The tool runs with the operator's process privileges; the operator is the gate. A platform-level policy adds a layer the operator already enforces by directory placement. Rejected by the owner; not in the shape.
- **Platform as secret dispatcher for tool credentials.** The agent forwards its own environment whole to installed tools and has no per-tool credential broker. Workspace grants resolve only variables already provisioned to that separate environment (ADR 0003, ADR 0013). There is no per-tool env scoping to configure either — the manifest field that looked like one was inert and is gone (#550) — so this is the standing answer to per-tool credentials rather than a preference between two available shapes.

## Open questions

- Authentication between the agent container and its sidecar (how the sidecar knows the caller is its pod's agent) — the gRPC listener ships pod-local and unauthenticated until this is decided.
- The shared-sidecar account model — with the multi-tenancy work.
- Authentication of installed tool servers and integrity attestation of fetched descriptors — operator-installed tools run with the platform's trust, so this matters when tools come from outside the operator's own build.
- Whether the untrusted-code path's checks have ever run where they are meant to. Deleting the privilege drop or the network isolation above now fails a privileged check rather than passing a green suite (#604, measured in `docs/research/mutation-survey/`), but the pipeline is failing account-wide (#603), so that check has been observed on a contributor's machine and not yet on the host.
